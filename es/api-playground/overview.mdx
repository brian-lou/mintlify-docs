El área de pruebas de API es un entorno interactivo que permite a los usuarios probar y explorar tus endpoints de API. Los desarrolladores pueden crear peticiones de API, enviarlas y ver las respuestas sin salir de tu documentación.

Consulta [Activar una actualización](/es/api/update/trigger) para ver un ejemplo del área de pruebas de API en acción.

El área de pruebas genera páginas interactivas para tus endpoints a partir de tu especificación OpenAPI o tu esquema AsyncAPI. Si modificas tu API, el área de pruebas actualiza automáticamente las páginas correspondientes.

Te recomendamos generar tu área de pruebas de API a partir de una especificación OpenAPI. Sin embargo, puedes crear manualmente páginas de referencia de API después de definir una URL base y un método de autenticación en tu `docs.json`.

<div id="get-started">
  ## Primeros pasos
</div>

<Steps>
  <Step title="Añade tu archivo de especificación OpenAPI.">
    <Tip>
      Valida tu archivo de especificación OpenAPI con [Swagger Editor](https://editor.swagger.io/) o con el comando de [Mint CLI](https://www.npmjs.com/package/mint) `mint openapi-check <filename>`.
    </Tip>

    ```bash {3}
    /your-project
      |- docs.json
      |- openapi.json
    ```
  </Step>

  <Step title="Genera páginas para endpoints.">
    Actualiza tu `docs.json` para que haga referencia a tu especificación OpenAPI.

    **Para generar automáticamente páginas para todos los endpoints de tu especificación OpenAPI**, añade una propiedad `openapi` a cualquier elemento de navegación.

    Este ejemplo genera una página para cada endpoint especificado en `openapi.json` y organiza las páginas en el grupo &quot;API reference&quot;.

    ```json Generar todas las páginas de endpoints
    "navigation": {
      "groups": [
        {
          "group": "API reference",
          "openapi": "openapi.json"
        }
      ]
    }
    ```

    **Para generar páginas solo para endpoints específicos**, enumera los endpoints en la propiedad `pages` del elemento de navegación.

    Este ejemplo genera páginas solo para los endpoints `GET /users` y `POST /users`. Para generar páginas de otros endpoints, añade endpoints adicionales al array `pages`.

    ```json Generar páginas de endpoints específicos
    "navigation": {
      "groups": [
          {
            "group": "API reference",
            "openapi": "openapi.json",
            "pages": [
              "GET /users",
              "POST /users"
            ]
          }
      ]
    }
    ```
  </Step>
</Steps>

<div id="customize-your-playground">
  ## Personaliza tu área de pruebas
</div>

Personaliza tu área de pruebas definiendo las siguientes propiedades en tu `docs.json`.

<ResponseField name="playground" type="object">
  Configuración del área de pruebas.

  <Expandable title="playground" defaultOpen="True">
    <ResponseField name="display" type="&#x22;interactive&#x22; | &#x22;simple&#x22; | &#x22;none&#x22; | &#x22;auth&#x22;">
      El modo de visualización del área de pruebas.

      * `"interactive"`: Muestra el área de pruebas interactiva.
      * `"simple"`: Muestra un endpoint copiable sin área de pruebas.
      * `"none"`: No muestra nada.
      * `"auth"`: Muestra el área de pruebas interactiva solo a los usuarios autenticados. Los usuarios no autenticados o que no pertenezcan a los grupos requeridos no verán ninguna área de pruebas.

      El valor predeterminado es `interactive`.
    </ResponseField>

    <ResponseField name="proxy" type="boolean" defaultOpen="True">
      Si las solicitudes a la API deben pasar por un servidor proxy. El valor predeterminado es `true`.
    </ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="examples" type="object">
  Configuración de los ejemplos de API generados automáticamente.

  <Expandable title="examples" defaultOpen="True">
    <ResponseField name="languages" type="array of string">
      Idiomas de ejemplo para los Snippet de API generados automáticamente.

      Los idiomas se muestran en el orden especificado.
    </ResponseField>

    <ResponseField name="defaults" type="&#x22;required&#x22; | &#x22;all&#x22;">
      Si se deben mostrar parámetros opcionales en los ejemplos de API. El valor predeterminado es `all`.
    </ResponseField>

    <ResponseField name="prefill" type="boolean">
      Si se debe rellenar previamente el área de pruebas con datos de ejemplos de esquemas. Cuando está habilitado, el área de pruebas completa automáticamente los campos de la solicitud con valores de ejemplo de tu especificación OpenAPI. El valor predeterminado es `false`.
    </ResponseField>

    <ResponseField name="autogenerate" type="boolean">
      Si se deben generar ejemplos de código para endpoints a partir de especificaciones de API. El valor predeterminado es `true`. Cuando se establece en `false`, solo aparecen en el área de pruebas los ejemplos de código escritos manualmente (desde `x-codeSamples` en las especificaciones OpenAPI o componentes `<RequestExample>` en MDX).
    </ResponseField>
  </Expandable>
</ResponseField>

<div id="example-configuration">
  ### Configuración de ejemplo
</div>

Este ejemplo configura el Área de pruebas de API para que sea interactiva, con Snippets de código de ejemplo para cURL, Python y JavaScript. En los Snippets de código solo se muestran los parámetros obligatorios, y el área de pruebas rellena previamente el cuerpo de la solicitud con valores de ejemplo.

```json
{
 "api": {
   "playground": {
     "display": "interactive"
   },
   "examples": {
     "languages": ["curl", "python", "javascript"],
     "defaults": "required",
     "prefill": true
   }
 }
}
```

<div id="auth-based-playground-display">
  ### Mostrar el área de pruebas según la autenticación
</div>

Usa el modo de visualización `auth` para mostrar el área de pruebas interactiva solo a los usuarios autenticados. Esto resulta útil cuando quieres que los usuarios puedan ver públicamente la documentación de tu API, pero limitar el acceso al área de pruebas a quienes hayan iniciado sesión.

Cuando `display` se establece en `auth`:

* Los usuarios autenticados ven el área de pruebas interactiva.
* Los usuarios no autenticados no ven ninguna área de pruebas (equivalente a `none`).

También puedes combinar `auth` con la propiedad `groups` en el Frontmatter de la página para restringir el acceso al área de pruebas a grupos de usuarios específicos.

```mdx Page with group-restricted playground
---
title: "Create user"
openapi: POST /users
playground: auth
groups: ["admin", "developer"]
public: true
---
```

En este ejemplo:

* La página es pública (cualquiera puede ver la documentación).
* Solo los usuarios autenticados que pertenecen a los grupos `admin` o `developer` ven el área de pruebas interactiva.
* Los usuarios que no pertenecen a esos grupos no ven el área de pruebas.

Si la página no tiene la propiedad `groups`, todos los usuarios autenticados ven el área de pruebas interactiva.

<Note>
  El modo de visualización `auth` requiere que la [autenticación](/es/deploy/authentication-setup) esté configurada para tu documentación.
</Note>

<div id="custom-endpoint-pages">
  ### Páginas personalizadas para endpoints
</div>

Cuando necesites más control sobre la documentación de tu API, usa la extensión `x-mint` en tu especificación OpenAPI o crea páginas MDX individuales para tus endpoints.

Ambas opciones te permiten:

* Personalizar los metadatos de la página
* Añadir contenido adicional, como ejemplos
* Controlar el comportamiento del área de pruebas en cada página

Se recomienda usar la extensión `x-mint` para que toda la documentación de tu API se genere automáticamente a partir de tu especificación OpenAPI y se mantenga en un solo archivo.

Se recomiendan las páginas MDX individuales para APIs pequeñas o cuando quieras probar cambios en páginas concretas.
