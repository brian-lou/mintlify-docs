Git es un sistema de control de versiones que registra los cambios en tu documentación y facilita la colaboración en equipo. Con Git, puedes ver qué ha cambiado en los archivos con el tiempo, quién hizo los cambios, cuándo los hizo y por qué. Git también te permite volver fácilmente a versiones anteriores de los archivos si necesitas deshacer cambios.

El editor web realiza operaciones de Git entre bastidores. Si entiendes Git, podrás trabajar de forma más eficaz con el editor web y colaborar con miembros del equipo que usan un entorno de desarrollo local.

<div id="why-git-for-documentation">
  ## ¿Por qué usar Git para la documentación?
</div>

Git ofrece capacidades esenciales para gestionar la documentación.

* **Historial de versiones**: Consulta qué cambió, cuándo y por qué en cada archivo.
* **Colaboración**: Varias personas pueden trabajar en distintas partes al mismo tiempo.
* **Seguridad**: Experimenta sin afectar la documentación publicada.
* **Flujos de revisión**: Los miembros del equipo pueden revisar los cambios antes de publicarlos.
* **Recuperación**: Deshaz cambios por error o restaura versiones anteriores.

<div id="new-to-git">
  ## ¿Aún no conoces Git?
</div>

Si estás empezando con Git y el control de versiones, aquí tienes una forma sencilla de comenzar.

<Steps>
  <Step title="Usa primero el editor web.">
    El [editor web](/es/editor/index) gestiona automáticamente las operaciones de Git.

    * Visualiza los cambios a medida que los haces.
    * Crea ramas con un solo clic.
    * Publica y crea pull requests sin usar comandos de Git.

    Así puedes aprender los conceptos de Git sin usar la línea de comandos.
  </Step>

  <Step title="Aprende sobre la marcha.">
    Cuando usas el editor web, ya estás usando Git.

    * **Guardar cambios** crea un commit.
    * **Crear rama** crea una rama de Git.
    * **Publicar** abre un pull request para revisión.
  </Step>

  <Step title="Explora el desarrollo local cuando te resulte útil.">
    Puedes gestionar toda tu documentación con el editor web y el panel, pero también puedes adaptar tu flujo de trabajo trabajando en tu entorno local.

    * Crea y edita archivos en tu editor favorito.
    * Usa Git desde la línea de comandos, GitHub Desktop o una extensión de tu editor.
    * Previsualiza los cambios localmente antes de publicarlos.
    * Intégralo con otras herramientas, como tickets de soporte, seguimiento de incidencias y sistemas de diseño.
  </Step>
</Steps>

<div id="core-git-concepts">
  ## Conceptos clave de Git
</div>

<AccordionGroup>
  <Accordion title="Rama">
    Una rama apunta a un commit específico de tu repositorio. Tu documentación publicada se genera a partir de una rama de despliegue. Puedes tener tantas otras ramas como quieras con cambios que aún no se hayan publicado en tu documentación. Si quieres incorporar los cambios de una rama a tu documentación publicada, puedes fusionarla con tu rama de despliegue mediante una pull request.

    Usa las ramas para trabajar en cambios sin afectar tu documentación publicada, probar nuevas funciones de forma segura y obtener revisiones antes de publicar.
  </Accordion>

  <Accordion title="Clonar">
    Descarga una copia completa de un repositorio en tu equipo, incluidos todos los archivos y todo el historial. Al clonar, obtienes todo lo necesario para trabajar en local.

    ```bash
    git clone https://github.com/your-org/your-repo
    ```
  </Accordion>

  <Accordion title="Commit">
    Una instantánea guardada de tus cambios en un momento concreto. Cada commit incluye un mensaje que describe qué cambió y crea un registro permanente en el historial de tu proyecto.
  </Accordion>

  <Accordion title="Conflicto">
    Se produce cuando dos personas cambian de forma distinta la misma parte de un archivo. Git te pide que elijas manualmente qué cambio conservar o que combines ambos cambios.
  </Accordion>

  <Accordion title="Rama de despliegue">
    La rama principal de tu proyecto. Los cambios en esta rama se publican automáticamente en tu sitio de documentación. Suele llamarse `main`, pero puedes configurar cualquier rama como rama de despliegue.
  </Accordion>

  <Accordion title="Diff">
    Un diff (o diferencia) muestra los cambios entre dos versiones de un archivo. Al revisar pull requests, los diffs resaltan qué ha cambiado con respecto a la versión original del archivo.
  </Accordion>

  <Accordion title="Fusionar">
    Combina cambios de una rama en otra. Normalmente se hace mediante una pull request después de la revisión para incorporar el trabajo de una funcionalidad a tu rama de despliegue.
  </Accordion>

  <Accordion title="Pull">
    Obtén los cambios más recientes del repositorio remoto en tu copia local. Así te mantienes al día con el trabajo de otras personas.

    ```bash
    git pull
    ```
  </Accordion>

  <Accordion title="Pull request">
    Una forma de proponer fusionar los cambios de una rama en tu documentación publicada. Permite revisar y comentar los cambios antes de que se publiquen. Suele llamarse PR, y en GitLab también se conoce como merge request.
  </Accordion>

  <Accordion title="Push">
    Envía tus commits locales al repositorio remoto. Esto pone tus cambios a disposición de otras personas y puede activar despliegues automáticos.

    ```bash
    git push
    ```
  </Accordion>

  <Accordion title="Remoto">
    Una versión de tu repositorio alojada en un servidor. Tu repositorio local se conecta a un repositorio remoto para enviar y recibir cambios.
  </Accordion>

  <Accordion title="Repositorio">
    El código fuente de tu documentación, con todos los archivos y su historial, que conforman las páginas de tu sitio de documentación. El editor web se conecta a tu repositorio de documentación para acceder al contenido y modificarlo.
  </Accordion>

  <Accordion title="Preparar">
    Prepara cambios concretos para incluirlos en tu próximo commit. El área de preparación te permite organizar los cambios en commits lógicos.

    ```bash
    git add filename.mdx
    ```
  </Accordion>
</AccordionGroup>

<div id="how-the-web-editor-uses-git">
  ## Cómo utiliza Git el editor web
</div>

El editor web se conecta a tu repositorio de Git mediante la [GitHub App](/es/deploy/github) o la [integración de GitLab](/es/deploy/gitlab) y automatiza las operaciones habituales de Git.

Cuando:

* **Abres un archivo**: El editor obtiene la versión más reciente de tu repositorio para garantizar que siempre trabajes con contenido actualizado.
* **Realizas cambios**: El editor guarda tus cambios como borrador, que puede convertirse en un commit cuando estés listo para guardar tu trabajo.
* **Guardas los cambios**: El editor crea un commit con tus cambios, lo que conserva tu trabajo en el historial del proyecto.
* **Creas una rama**: El editor crea una nueva rama en tu repositorio que cualquier persona con acceso puede usar para colaborar y revisar cambios.
* **Publicas en tu rama de despliegue**: El editor hace commit y push directamente a tu rama de despliegue, lo que publica tus cambios de inmediato.
* **Publicas en otras ramas**: El editor crea una pull request, lo que te permite recibir comentarios de otras personas antes de fusionar tus cambios en tu rama de despliegue.

<div id="common-workflows">
  ## Flujos de trabajo comunes
</div>

<div id="publish-directly-to-your-deployment-branch">
  ### Publica directamente en tu rama de despliegue
</div>

<Tabs>
  <Tab title="Con el editor web">
    1. Abre el archivo en el [editor web](https://dashboard.mintlify.com/editor).
    2. Realiza los cambios.
    3. Haz clic en **Publicar**.
    4. Los cambios aparecen en el repositorio y se despliegan automáticamente.
  </Tab>

  <Tab title="Con desarrollo local">
    1. Descarga los cambios más recientes: `git pull`
    2. Edita el archivo en tu editor.
    3. Prepara los cambios: `git add filename.mdx`
    4. Haz commit: `git commit -m "Update documentation"`
    5. Haz push: `git push`
    6. Los cambios se despliegan automáticamente.
  </Tab>
</Tabs>

<div id="work-on-a-feature-branch">
  ### Trabaja en una rama de funcionalidad
</div>

<Tabs>
  <Tab title="Con el editor web">
    <Note>
      Para crear pull requests desde el editor web, debes tener activada una regla de protección de ramas que exija pull requests antes de fusionar cambios en tu rama de despliegue. Sin reglas de protección de ramas, los cambios de las ramas se fusionan en tu rama de despliegue al publicarse.
    </Note>

    1. Crea una rama desde el menú desplegable de ramas en la barra de herramientas del editor.
    2. Haz y guarda los cambios en la rama.
    3. Haz clic en **Publicar** para crear una pull request.
    4. Fusiona la pull request cuando esté lista.
  </Tab>

  <Tab title="Con desarrollo local">
    1. Crea una rama: `git checkout -b feature-name`
    2. Haz los cambios y confirma el commit.
    3. Sube la rama: `git push -u origin feature-name`
    4. Crea una pull request.
    5. Fusiona la pull request cuando esté lista.
  </Tab>
</Tabs>

<div id="review-changes-before-publishing">
  ### Revisa los cambios antes de publicarlos
</div>

<Steps>
  <Step title="Crea una rama de funcionalidad.">
    Trabaja en una rama distinta de la rama de despliegue para poder compartir y revisar los cambios antes de publicarlos.
  </Step>

  <Step title="Haz tus cambios.">
    Edita los archivos y haz commit de los cambios en la rama de funcionalidad.
  </Step>

  <Step title="Crea una pull request.">
    Crea una pull request para proponer fusionar los cambios de tu rama de funcionalidad en la rama de despliegue.
  </Step>

  <Step title="Revisa el diff.">
    Comprueba tus cambios. La pull request muestra las diferencias línea por línea con respecto a la versión original del archivo.
  </Step>

  <Step title="Recibe comentarios del equipo.">
    Los miembros del equipo pueden dejar comentarios en líneas específicas o sobre los cambios en general. Haz los cambios necesarios y confírmalos en la rama de funcionalidad.
  </Step>

  <Step title="Fusiona cuando se apruebe.">
    Fusiona la pull request para publicar los cambios en tu documentación en producción.
  </Step>
</Steps>

<div id="git-best-practices">
  ## Buenas prácticas de Git
</div>

Cada equipo desarrolla sus propios flujos de trabajo y preferencias, pero estas son algunas buenas prácticas generales para empezar.

* **Escribe mensajes de commit descriptivos**: Sé específico sobre lo que cambió y usa un lenguaje activo. `Fix broken link in API docs` es más informativo que `update page`.
* **Usa nombres de rama descriptivos**: Los nombres de las ramas deben explicar su propósito. Usa nombres informativos como `update-api-reference` en lugar de nombres genéricos como `temp` o `my-branch`.
* **Mantén las ramas centradas en una sola cosa**: Haz que los cambios de una rama se limiten a una tarea o proyecto específicos. Esto facilita las revisiones y reduce los conflictos.
* **Elimina las ramas después de fusionarlas**: Elimina las ramas cuando ya no las necesites para mantener tu repositorio ordenado.
* **Haz pull antes de hacer push**: Haz siempre pull de los cambios más recientes antes de hacer push para evitar conflictos. El editor web lo hace automáticamente.
* **Revisa primero tus propios cambios**: Revisa el diff antes de crear una pull request.
