Git es un sistema de control de versiones que registra los cambios en tu documentación y permite la colaboración en equipo. Con Git, puedes ver qué ha cambiado a lo largo del tiempo en los archivos, quién hizo los cambios, cuándo los hizo y por qué. Git también facilita volver a versiones anteriores de los archivos si necesitas deshacer cambios.

El editor web realiza operaciones de Git en segundo plano. Con conocimientos de Git, puedes trabajar de manera más efectiva con el editor web y colaborar con los miembros del equipo que usan desarrollo local.

<div id="why-git-for-documentation">
  ## ¿Por qué Git para la documentación?
</div>

Git proporciona capacidades esenciales para gestionar la documentación.

* **Historial de versiones**: Ver qué cambió, cuándo y por qué en cada archivo.
* **Colaboración**: Varias personas pueden trabajar en diferentes partes simultáneamente.
* **Seguridad**: Experimentar sin afectar la documentación en producción.
* **Flujos de revisión**: Los miembros del equipo pueden revisar los cambios antes de publicarlos.
* **Recuperación**: Deshacer errores o restaurar versiones anteriores.

<div id="new-to-git">
  ## ¿Nuevo en Git?
</div>

Si eres completamente nuevo en Git y al control de versiones, aquí tienes una ruta para empezar.

<Steps>
  <Step title="Usa primero el editor web.">
    El [editor web](/es/editor/index) gestiona las operaciones de Git automáticamente.

    * Mira visualmente cualquier cambio a medida que lo haces.
    * Crea ramas con un solo clic.
    * Publica y crea pull requests sin usar comandos de Git.

    Esto te permite aprender los conceptos de Git sin usar la línea de comandos.
  </Step>

  <Step title="Aprende haciendo.">
    A medida que usas el editor web, estás usando Git.

    * **Save changes** crea un commit.
    * **Create branch** crea una rama de Git.
    * **Publish** abre un pull request para revisión.
  </Step>

  <Step title="Explora el desarrollo local cuando te resulte útil.">
    Puedes gestionar tu documentación completamente con el editor web y el panel, pero puedes personalizar tu flujo de trabajo trabajando en tu entorno local.

    * Crea y edita archivos en tu editor favorito.
    * Usa Git en la línea de comandos, GitHub Desktop o una extensión en tu editor.
    * Previsualiza los cambios localmente antes de publicar.
    * Intégralo con otras herramientas como tickets de soporte, seguimiento de incidencias y sistemas de diseño.
  </Step>
</Steps>

<div id="core-git-concepts">
  ## Conceptos fundamentales de Git
</div>

<AccordionGroup>
  <Accordion title="Rama">
    Una rama apunta a un commit específico en tu repositorio. Tu documentación publicada se genera a partir de una rama de despliegue. Puedes tener cualquier número de otras ramas con cambios que aún no se han publicado en tu documentación. Si quieres incorporar los cambios de una rama en tu documentación publicada, puedes fusionar esa rama en tu rama de despliegue mediante una pull request.

    Usa ramas para trabajar en cambios sin afectar tu documentación publicada, experimentar de forma segura con nuevas funcionalidades y recibir revisiones antes de publicar.
  </Accordion>

  <Accordion title="Clonar">
    Descarga una copia completa de un repositorio en tu computadora, incluyendo todos los archivos y el historial completo. Cuando clonas, obtienes todo lo necesario para trabajar de forma local.

    ```bash
    git clone https://github.com/your-org/your-repo
    ```
  </Accordion>

  <Accordion title="Commit">
    Una instantánea guardada de tus cambios en un momento específico. Cada commit incluye un mensaje que describe qué cambió y crea un registro permanente en el historial de tu proyecto.
  </Accordion>

  <Accordion title="Conflicto">
    Ocurre cuando dos personas cambian de forma diferente la misma parte de un archivo. Git te pide que elijas manualmente qué cambio conservar o si debes combinar ambos cambios.
  </Accordion>

  <Accordion title="Rama de despliegue">
    La rama principal de tu proyecto. Los cambios en esta rama se publican automáticamente en tu sitio de documentación. A menudo se llama `main`, pero puedes configurar cualquier rama como tu rama de despliegue.
  </Accordion>

  <Accordion title="Diff">
    Un diff (o diferencia) muestra los cambios entre dos versiones de un archivo. Al revisar pull requests, los diffs resaltan qué es diferente con respecto a la versión original del archivo.
  </Accordion>

  <Accordion title="Fusionar">
    Combina cambios de una rama en otra. Normalmente se hace mediante una pull request, después de la revisión, para incorporar el trabajo de una funcionalidad en tu rama de despliegue.
  </Accordion>

  <Accordion title="Pull">
    Obtiene los cambios más recientes desde el repositorio remoto a tu copia local. Te mantiene al día con el trabajo de otras personas.

    ```bash
    git pull
    ```
  </Accordion>

  <Accordion title="Pull request">
    Una forma de proponer fusionar tus cambios en una rama con tu documentación publicada. Permite la revisión y discusión antes de que los cambios se publiquen. Se conoce comúnmente como PR y también se llama merge request en GitLab.
  </Accordion>

  <Accordion title="Push">
    Envía tus commits locales al repositorio remoto. Esto hace que tus cambios estén disponibles para otras personas y puede activar despliegues automáticos.

    ```bash
    git push
    ```
  </Accordion>

  <Accordion title="Remoto">
    Una versión de tu repositorio alojada en un servidor. Tu repositorio local se conecta a un repositorio remoto para enviar (push) y obtener (pull) cambios.
  </Accordion>

  <Accordion title="Repositorio">
    El código fuente de tu documentación, con todos los archivos y su historial, que conforman las páginas de tu sitio de documentación. El editor web se conecta a tu repositorio de documentación para acceder al contenido y modificarlo.
  </Accordion>

  <Accordion title="Preparar (stage)">
    Prepara cambios específicos para incluirlos en tu próximo commit. Preparar cambios te permite organizarlos en commits lógicos.

    ```bash
    git add filename.mdx
    ```
  </Accordion>
</AccordionGroup>

<div id="how-the-web-editor-uses-git">
  ## Cómo usa Git el editor web
</div>

El editor web se conecta a tu repositorio de Git a través de la [GitHub App](/es/deploy/github) o de la [integración con GitLab](/es/deploy/gitlab) y automatiza operaciones comunes de Git.

Cuando haces lo siguiente:

* **Abres un archivo**: El editor obtiene la versión más reciente de tu repositorio para que siempre trabajes con contenido actualizado.
* **Haces cambios**: El editor guarda tus cambios como un borrador que puede convertirse en un commit cuando estés listo para guardar tu trabajo.
* **Guardas cambios**: El editor hace un commit con tus cambios, preservando tu trabajo en el historial del proyecto.
* **Creas una rama**: El editor crea una nueva rama en tu repositorio que cualquiera con acceso al repositorio puede usar para colaborar y revisar cambios.
* **Publicas en tu rama de despliegue**: El editor hace un commit y hace push directamente a tu rama de despliegue, lo que publica tus cambios de inmediato.
* **Publicas en otras ramas**: El editor crea una pull request, lo que te permite recibir comentarios de otras personas antes de fusionar tus cambios en tu rama de despliegue.

<div id="common-workflows">
  ## Flujos de trabajo habituales
</div>

<div id="publish-directly-to-your-deployment-branch">
  ### Publica directamente en tu rama de despliegue
</div>

<Tabs>
  <Tab title="Usando el editor web">
    1. Abre el archivo en el [editor web](https://dashboard.mintlify.com/editor).
    2. Realiza los cambios.
    3. Haz clic en **Publish**.
    4. Los cambios aparecen en el repositorio y se despliegan automáticamente.
  </Tab>

  <Tab title="Usando el desarrollo local">
    1. Obtén los últimos cambios: `git pull`
    2. Edita el archivo en tu editor.
    3. Añade los cambios: `git add filename.mdx`
    4. Realiza un commit: `git commit -m "Update documentation"`
    5. Haz push: `git push`
    6. Los cambios se despliegan automáticamente.
  </Tab>
</Tabs>

<div id="work-on-a-feature-branch">
  ### Trabajar en una rama de funcionalidad
</div>

<Tabs>
  <Tab title="Usar el editor web">
    <Note>
      Para crear pull requests desde el editor web, debes tener una regla de protección de ramas habilitada que requiera pull requests antes de que los cambios puedan fusionarse con tu rama de despliegue. Sin reglas de protección de ramas, los cambios en las ramas se fusionan con tu rama de despliegue cuando se publican.
    </Note>

    1. Crea una rama desde el menú desplegable de ramas en la barra de herramientas del editor.
    2. Realiza y guarda los cambios en la rama.
    3. Haz clic en **Publish** para crear un pull request.
    4. Fusiona el pull request cuando esté listo.
  </Tab>

  <Tab title="Usar el desarrollo local">
    1. Crea una rama: `git checkout -b feature-name`
    2. Realiza y confirma (commit) los cambios.
    3. Envía la rama (push): `git push -u origin feature-name`
    4. Crea un pull request.
    5. Fusiona el pull request cuando esté listo.
  </Tab>
</Tabs>

<div id="review-changes-before-publishing">
  ### Revisar los cambios antes de publicar
</div>

<Steps>
  <Step title="Crear una rama de funcionalidad.">
    Trabaja en los cambios en una rama distinta de tu rama de despliegue para que puedas compartir y revisar los cambios antes de publicar.
  </Step>

  <Step title="Haz tus cambios.">
    Edita los archivos y haz commit de los cambios en la rama de funcionalidad.
  </Step>

  <Step title="Crea una pull request.">
    Crea una pull request para proponer fusionar los cambios de tu rama de funcionalidad en la rama de despliegue.
  </Step>

  <Step title="Revisa el diff.">
    Revisa tus cambios. La pull request muestra las diferencias línea por línea con respecto a la versión original del archivo.
  </Step>

  <Step title="Obtén comentarios del equipo.">
    Los miembros del equipo pueden comentar líneas específicas o los cambios en general. Realiza los cambios necesarios y haz commit de ellos en la rama de funcionalidad.
  </Step>

  <Step title="Fusiona cuando esté aprobado.">
    Fusiona la pull request para publicar los cambios en tu documentación publicada.
  </Step>
</Steps>

<div id="git-best-practices">
  ## Mejores prácticas de Git
</div>

Cada equipo desarrolla sus propios flujos de trabajo y preferencias, pero estas son algunas buenas prácticas generales para comenzar.

* **Escribe mensajes de commit descriptivos**: Sé específico sobre los cambios realizados y usa un lenguaje activo. `Fix broken link in API docs` es más informativo que `update page`.
* **Usa nombres de ramas descriptivos**: Los nombres de las ramas deben explicar el propósito de la rama. Usa nombres informativos como `update-api-reference` en lugar de nombres genéricos como `temp` o `my-branch`.
* **Mantén las ramas enfocadas**: Mantén los cambios en una rama centrados en una tarea o proyecto específico. Esto facilita las revisiones y reduce los conflictos.
* **Elimina las ramas después de hacer merge**: Elimina las ramas cuando ya no las necesites para mantener tu repositorio ordenado.
* **Haz pull antes de hacer push**: Siempre haz pull de los cambios más recientes antes de hacer push para evitar conflictos. El editor web hace esto automáticamente.
* **Revisa primero tus propios cambios**: Revisa el diff antes de crear un pull request.
