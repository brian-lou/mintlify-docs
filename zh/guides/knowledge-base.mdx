内部知识库可以帮助团队更快找到答案，并维护单一可信信息源。如果团队信息分散在不同渠道和平台中，大家在查找答案时，可能会找到不准确的信息，甚至什么也找不到。集中式知识库通过将答案统一放在所有人都能找到的地方，并为团队提供一个专门记录共享知识的位置，来解决这个问题。

Mintlify 为知识库提供所需的基础设施，让整个团队都能参与内容贡献。

* **AI 驱动的搜索**：[助手](/zh/ai/assistant) 会基于您的知识库内容回答问题，因此即使用户不清楚该去哪里找，也能获得答案。
* **Slack 集成**：将 助手 添加到 [Slack](/zh/ai/slack-bot) 中，让团队成员可以直接提问，并使用 [agent](/zh/agent/slack) 从对话中沉淀知识。
* **低门槛贡献**：[网页编辑器](/zh/editor) 和 [agent](/zh/agent/quickstart) 让团队中的任何人都能在无需学习 Git 或 Markdown 的情况下更新内容。
* **内置身份验证**：使用 [SSO or OAuth](/zh/deploy/authentication-setup) 控制访问权限，并通过 [groups](/zh/deploy/authentication-setup#control-access-with-groups) 为不同团队显示不同内容。

<div id="prerequisites">
  ## 前提条件
</div>

如果你还没有创建 Mintlify 项目，请参阅[快速入门](/zh/quickstart)来部署你的站点。

* 身份验证系统 (SSO 或 Okta、Azure AD 等 OAuth 提供商)
* 对用于托管的域名拥有控制权
* 具有 Mintlify 组织的管理员访问权限

<div id="migrate-existing-content">
  ## 迁移现有内容
</div>

如果你是从零开始创建知识库，请直接跳到[设计导航结构](#design-the-navigation-structure)。

<div id="audit-existing-content">
  ### 盘点现有内容
</div>

梳理你当前知识库中已有的内容。这有助于你明确哪些内容需要迁移，规划如何在新知识库中组织这些内容，找出内容缺口，并确认所有内容都已迁移到新知识库中。

* **文章总数**：帮助估算迁移工作量并跟踪迁移完整性。
* **主题和内容**：为导航结构和内容组织提供依据。
* **当前组织方式**：了解内容目前的组织方式，以及是否符合你期望的结构。
* **内容类型**：确定文本、PDF、视频和嵌入内容是否需要进行转换。
* **元数据**：识别需要保留的元数据，例如日期、作者和标签。
* **访问要求**：为知识库确定最合适的身份验证方案。

<div id="export-your-existing-content">
  ### 导出现有内容
</div>

大多数知识库平台都支持以标准格式导出内容。具体选择哪种格式，取决于你当前使用的平台和你的优先事项。

* 导出为 **Markdown**，可最轻松地迁移到 Mintlify。 (推荐)
* 如果不支持 Markdown，则导出为 **HTML**。你之后必须将内容转换为 Markdown。
* 如果有需要保留的结构化元数据，则导出为 **JSON 或 CSV**。

<div id="design-the-navigation-structure">
  ## 设计导航结构
</div>

导航结构决定了用户如何在知识库中找到所需内容。你可以沿用现有结构，也可以重新设计，使其更符合团队对内容的理解和组织方式。

<Tip>
  迁移也是优化结构的好时机。可以考虑一下当前的组织方式是否真的适合你的团队，或者是否可以重新整理内容，让信息更容易查找。
</Tip>

你的 `docs.json` 文件定义了知识库的导航结构。在项目仓库的根目录创建此文件。

```json
{
  "navigation": {
    "groups": [
      {
        "group": "Finance",
        "pages": [
            "finance/overview",
            "finance/budgeting-process",
            "finance/expense-reports",
            "finance/cost-allocation"
        ]
      },
      {
        "group": "HR",
        "pages": [
            "hr/overview",
            "hr/onboarding",
            "hr/benefits",
            "hr/time-off-policy"
        ]
      },
      {
        "group": "Engineering",
        "pages": [
          "engineering/overview",
          "engineering/dev-setup",
          "engineering/deployment",
          "engineering/code-standards"
        ]
      }
    ]
  }
}
```

有关如何构建知识库结构的更多信息，请参阅 [Navigation](/zh/organize/navigation)。

<div id="set-up-authentication">
  ## 设置身份验证
</div>

确定谁需要访问知识库中的哪些内容。

如果所有人都应能访问整个知识库，只需设置[身份验证](/zh/deploy/authentication-setup)。

如果你需要将某些内容仅开放给特定用户或用户组，请设置带有[基于用户组的访问控制](/zh/deploy/authentication-setup#control-access-with-groups)的身份验证。

<div id="migrate-your-content">
  ## 迁移内容
</div>

将导出的内容移到与您设计的导航结构一致的文件夹结构中。根据需要将内容转换为 Markdown，补充缺失的前置元数据，并设置内部链接。

<Steps>
  <Step title="整理文件">
    创建与您的 `docs.json` 结构对应的文件夹。例如，如果您的 `docs.json` 中有一个 Finance 分组，请创建一个 `finance/` 文件夹：

    ```text
    your-project/
    ├── docs.json
    ├── finance/
    │   ├── overview.mdx
    │   ├── budgeting-process.mdx
    │   ├── expense-reports.mdx
    │   └── cost-allocation.mdx
    ├── hr/
    │   ├── overview.mdx
    │   ├── onboarding.mdx
    │   ├── benefits.mdx
    │   └── time-off-policy.mdx
    └── engineering/
        ├── overview.mdx
        ├── dev-setup.mdx
        ├── deployment.mdx
        └── code-standards.mdx
    ```

    将每篇文章放到对应的文件夹中。文件路径必须与 `docs.json` 中的路径一致。例如，如果 `docs.json` 引用了 `"finance/expense-reports"`，则项目仓库中的文件应为 `finance/expense-reports.mdx`。
  </Step>

  <Step title="为每篇文章添加前置元数据">
    每个 `.mdx` 文件顶部都需要包含前置元数据。每个页面都必须有标题和描述。有关页面元数据的更多信息，请参阅 [Pages](/zh/organize/pages)。

    ```mdx
    ---
    title: "Expense Report Process"
    description: "How to submit and track expense reports"
    ---

    Your content here...
    ```
  </Step>

  <Step title="设置内部链接">
    使用相对于项目根目录的路径在页面之间建立链接。

    ```mdx
    See [Onboarding Guide](/hr/onboarding) for new employee setup.

    For questions, contact [HR Benefits Team](/hr/benefits#common-questions).
    ```
  </Step>

  <Step title="将 HTML 和其他格式转换为 Markdown">
    如果您导出的内容是 HTML，请将其转换为 Markdown。可用的工具包括：

    * **Pandoc**：可在多种格式之间转换的命令行工具。
    * **CloudConvert**：支持 HTML、DOCX、PDF 等格式的在线转换工具。
    * **VS Code extensions**：在扩展中搜索 “HTML to Markdown”。
  </Step>

  <Step title="处理多种内容格式">
    如果您有 PDF、视频或其他媒体，请决定如何将它们纳入知识库。

    * **嵌入视频**：直接嵌入视频，或链接到托管的视频。
    * **链接到 PDF**：将 PDF 添加到项目仓库中，并从相关页面链接到这些文件。
    * **将 PDF 转换为 Markdown**：如果您希望将 PDF 内容作为页面展示，请将 PDF 转换为 Markdown。
  </Step>
</Steps>

<div id="set-up-the-assistant">
  ## 设置助手
</div>

Pro 和 Enterprise 套餐默认会自动启用助手。借助助手，你的团队可以提问，并从知识库中获得附带引用来源的答案。

在你的[控制面板](https://dashboard.mintlify.com/products/assistant/settings)中配置助手：

* **示例问题**：添加常见问题，例如“如何提交报销单”或“休假政策是什么”，让用户一键即可获得答案。
* **搜索站点**：添加助手在回答问题时可搜索的其他站点。
* **转接邮箱**：为助手无法回答的问题设置一个支持邮箱。

<div id="add-the-assistant-to-slack">
  ### 将助手添加到 Slack
</div>

[Slack 机器人](/zh/ai/slack-bot) 可让你的团队无需离开 Slack 即可向助手提问。你可以创建一个由机器人回复每条消息的频道，也可以让团队成员在任何频道中通过 @mention 机器人来提问。

<div id="enable-team-contributions">
  ## 启用团队成员协作
</div>

知识库要保持准确，就不能只靠最初搭建它的人维护，而应让每个人都能参与更新。Mintlify 提供了三种方式，帮助团队成员快速为你的知识库做出贡献。

<div id="web-editor">
  ### 网页编辑器
</div>

[网页编辑器](/zh/editor) 让任何人都能在浏览器中创建和编辑页面。贡献者可以：

* 以可视化方式或使用 Markdown 编辑页面。
* 通过拖放调整导航结构。
* 上传图片和媒体文件。
* 创建分支和拉取请求以供审核。

这非常适合熟悉内容、但不熟悉代码工作流的主题专家。

<div id="agent">
  ### Agent
</div>

控制面板中的 [agent](/zh/agent/quickstart) 可根据自然语言提示生成文档更新。描述你想要修改的内容，agent 就会创建一个包含这些更新的拉取请求。

例如，团队成员可以提示“在费用政策页面中新增一节，说明如何提交金额超过 50 美元的餐费收据”，并将现有的费用政策页面复制到提示中。agent 会起草内容并创建一个 PR 供审核。

<div id="capture-knowledge-from-slack">
  ### 从 Slack 中获取知识
</div>

团队经常会在 Slack 中分享有价值的信息，但这些内容往往不会被写进文档。[Slack 中的agent](/zh/agent/slack)可以获取这些知识，并将其整理为结构化文档。

当有人在 Slack 线程中分享了有用信息时，任何团队成员都可以提及 `@mintlify`，并说明要如何将其记录成文档。该agent会读取对话内容，提取相关信息，并创建一个拉取请求。这很适合在上下文还很清晰时，记录技术决策、故障排查方案和流程说明。

例如，如果你的团队在线程中讨论了如何配置新的集成，你可以回复：

> @mintlify 根据这段对话创建一份关于配置 Acme 集成的指南。

该agent会利用线程中的上下文创建文档，记录讨论中的关键信息。

<div id="locally">
  ### 在本地
</div>

任何有权访问你的知识库仓库的人，都可以在自己偏好的编辑器中本地工作，并将更改推送到你的仓库。

<div id="establish-maintenance-workflows">
  ## 建立维护工作流
</div>

知识库如果缺乏维护，很快就会过时。建立相应机制，确保内容保持最新，并帮助团队成员持续为知识库做出贡献。

<Steps>
  <Step title="明确内容负责人">
    为每个章节指定一位负责人或一个小团队。他们不必撰写所有内容，但需要负责：

    * 定期审查内容。
    * 标记过时信息。
    * 审批所属章节中的新页面。
    * 在有人反馈错误时及时响应。
  </Step>

  <Step title="建立审查周期和内容核验机制">
    内容会随着时间推移而陈旧。请制定审查计划。

    * **关键内容**：每 30 天审查一次
    * **常规内容**：每 90 天审查一次
    * **长期有效内容**：每年审查一次

    审查时，请检查：

    * 链接是否仍然有效？
    * 系统或流程是否发生了变化？
    * 示例是否仍然适用？
    * 是否有需要补充的新信息？
  </Step>

  <Step title="制定贡献指南">
    让任何人都能轻松改进知识库。你的指南应涵盖：

    * **格式**：是否有特定模板或格式要求？
    * **流程**：应如何提出并提交更改？
    * **审查**：由谁审查提交内容？处理周期是多久？
    * **范围**：哪些类型的内容属于涵盖范围？
  </Step>

  <Step title="监控使用指标">
    查看团队如何使用知识库，以便确定内容优先级并找出可改进的地方。为审查使用指标设定固定频率——每月或每季度都是不错的间隔。

    * 哪些文章浏览量最高？应优先确保这些内容准确且易读。
    * 哪些文章没有浏览量？可以考虑删除，或提升其可发现性。
    * 跳出率是多少？如果用户进入后立即离开，可能说明内容帮助不大，或者导航还有改进空间。
  </Step>
</Steps>

<div id="next-steps">
  ## 后续步骤
</div>

你的知识库已准备就绪，可以发布了。部署后：

1. 向团队宣布知识库已上线。
2. 在分析工具中监测使用情况和搜索行为。
3. 当人们发现内容缺口时，鼓励他们参与补充。
4. 定期审查并更新内容。

最成功的知识库会根据团队的实际使用情况不断演进。
