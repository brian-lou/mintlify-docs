内部知识库可以帮助你的团队快速找到答案，并维护单一可信的信息来源。如果团队的信息分散在不同渠道和平台上，人们在搜索答案时可能会找到不准确的信息，甚至什么也找不到。集中式知识库通过把答案集中到所有人都能找到的地方，并为团队提供专门记录共享知识的空间来解决这个问题。

Mintlify 提供基础设施，帮助你搭建一个全员都能参与维护的知识库。

* **AI 驱动搜索**： [assistant](/zh/ai/assistant) 使用你的知识库内容回答问题，让人们即使不知道具体到哪里查找，也能获得答案。
* **Slack 集成**：将 assistant 添加到 [Slack](/zh/ai/slack-bot)，让团队可以提问，并使用 [agent](/zh/agent/slack) 从对话中沉淀知识。
* **低门槛贡献**：通过 [web editor](/zh/editor) 和 [agent](/zh/agent/quickstart)，团队中的任何人都可以更新内容，而无需学习 Git 或 Markdown。
* **内置身份验证**：通过 [SSO 或 OAuth](/zh/deploy/authentication-setup) 控制访问权限，并使用 [groups](/zh/deploy/authentication-setup#control-access-with-groups) 向不同团队展示不同内容。

<div id="prerequisites">
  ## 前提条件
</div>

如果你还没有创建 Mintlify 项目，请参阅[快速开始](/zh/quickstart)来部署你的网站。

* 一个身份验证系统（SSO 或 Okta、Azure AD 等 OAuth 提供商）
* 对用于托管的域名拥有控制权
* 对你的 Mintlify 组织拥有管理员权限

<div id="migrate-existing-content">
  ## 迁移现有内容
</div>

如果你是从头开始创建知识库，请跳至[设计导航结构](#design-the-navigation-structure)。

<div id="audit-existing-content">
  ### 审核现有内容
</div>

盘点你当前知识库中已有的所有内容。这有助于你了解需要迁移哪些内容、规划如何在新的知识库中组织这些内容、识别内容中的任何空白，并确认你已将所有内容迁移到新的知识库中。

* **文章总数**：帮助估算迁移工作量并跟踪迁移完成情况。
* **主题和内容**：为导航结构设计和内容组织提供依据。
* **当前组织方式**：查看内容目前的组织方式，以及它是否符合你期望的结构。
* **内容类型**：确定针对文本、PDF、视频和嵌入内容的转换需求。
* **元数据**：识别需要保留的元数据，例如日期、作者和标签。
* **访问要求**：确定适合你的知识库的身份验证方式。

<div id="export-your-existing-content">
  ### 导出现有内容
</div>

大多数知识库平台都支持将内容导出为标准格式。你选择的格式取决于当前所用的平台以及你的需求侧重点。

* 导出为 **Markdown**，以最简单的方式迁移到 Mintlify。（推荐）
* 如果不支持导出为 Markdown，则导出为 **HTML**。之后你需要将内容转换为 Markdown。
* 如果你有需要保留的结构化元数据，可以导出为 **JSON 或 CSV**。

<div id="design-the-navigation-structure">
  ## 设计导航结构
</div>

导航结构决定了人们如何在你的知识库中查找内容。你可以沿用现有的结构，或者重新设计，使其更符合你团队对内容的理解和使用方式。

<Tip>
  迁移是改进结构的好时机。思考一下你当前的组织方式是否真的适合团队，或者是否可以重新规划，让信息更容易被找到。
</Tip>

你的 `docs.json` 文件定义了知识库的导航结构。请在项目仓库的根目录创建这个文件。

```json
{
  "navigation": {
    "groups": [
      {
        "group": "Finance",
        "pages": [
            "finance/overview",
            "finance/budgeting-process",
            "finance/expense-reports",
            "finance/cost-allocation"
        ]
      },
      {
        "group": "HR",
        "pages": [
            "hr/overview",
            "hr/onboarding",
            "hr/benefits",
            "hr/time-off-policy"
        ]
      },
      {
        "group": "Engineering",
        "pages": [
          "engineering/overview",
          "engineering/dev-setup",
          "engineering/deployment",
          "engineering/code-standards"
        ]
      }
    ]
  }
}
```

关于如何组织知识库结构的更多信息，请参阅[导航](/zh/organize/navigation)。

<div id="set-up-authentication">
  ## 设置身份验证
</div>

确定在你的知识库中，谁需要访问哪些内容。

如果所有人都应当能够访问整个知识库，则只需设置[身份验证](/zh/deploy/authentication-setup)。

如果你需要将某些内容的访问权限限制为特定用户或用户组，请设置带有[基于用户组的访问控制](/zh/deploy/authentication-setup#control-access-with-groups)的身份验证。

<div id="migrate-your-content">
  ## 迁移内容
</div>

将导出的内容移动到与你设计的导航结构相匹配的文件夹结构中。如有需要，将内容转换为 Markdown，补全缺失的 frontmatter，并设置内部链接。

<Steps>
  <Step title="整理文件">
    创建与你的 `docs.json` 结构相对应的文件夹。例如，如果你的 `docs.json` 中有一个 Finance 分组，就创建一个 `finance/` 文件夹：

    ```text
    your-project/
    ├── docs.json
    ├── finance/
    │   ├── overview.mdx
    │   ├── budgeting-process.mdx
    │   ├── expense-reports.mdx
    │   └── cost-allocation.mdx
    ├── hr/
    │   ├── overview.mdx
    │   ├── onboarding.mdx
    │   ├── benefits.mdx
    │   └── time-off-policy.mdx
    └── engineering/
        ├── overview.mdx
        ├── dev-setup.mdx
        ├── deployment.mdx
        └── code-standards.mdx
    ```

    将每篇文章放在对应的文件夹中。文件路径必须与 `docs.json` 中的路径一致。例如，如果 `docs.json` 中引用 `"finance/expense-reports"`，则项目仓库中的文件应为 `finance/expense-reports.mdx`。
  </Step>

  <Step title="为每篇文章添加 frontmatter">
    每个 `.mdx` 文件在顶部都需要包含带有元数据的 frontmatter。每个页面都需要标题和描述。有关页面元数据的更多信息，请参阅 [Pages](/zh/organize/pages)。

    ```mdx
    ---
    title: "Expense Report Process"
    description: "How to submit and track expense reports"
    ---

    Your content here...
    ```
  </Step>

  <Step title="设置内部链接">
    使用从项目根目录开始的路径在页面之间创建链接。

    ```mdx
    See [Onboarding Guide](/hr/onboarding) for new employee setup.

    For questions, contact [HR Benefits Team](/hr/benefits#common-questions).
    ```
  </Step>

  <Step title="将 HTML 和其他格式转换为 Markdown">
    如果你将内容导出为 HTML，请将其转换为 Markdown。可以提供帮助的一些工具包括：

    * **Pandoc**：一个可在多种格式之间转换的命令行工具。
    * **CloudConvert**：支持 HTML、DOCX、PDF 等格式的在线转换工具。
    * **VS Code 扩展**：在扩展市场中搜索 “HTML to Markdown”。
  </Step>

  <Step title="处理多种内容格式">
    如果你有 PDF、视频或其他媒体，请决定如何将它们纳入你的知识库。

    * **嵌入视频**：将视频直接嵌入页面，或链接到托管平台上的视频。
    * **链接到 PDF**：将 PDF 添加到项目仓库，并从相关页面链接到它们。
    * **将 PDF 转换为 Markdown**：如果你希望 PDF 的内容以页面形式呈现，请将 PDF 转换为 Markdown。
  </Step>
</Steps>

<div id="set-up-the-assistant">
  ## 设置助手
</div>

在 Pro 和 Enterprise 订阅计划中会自动启用助手。通过助手，你的团队可以就知识库提问，并获得附带引用来源的回答。

在你的[控制台](https://dashboard.mintlify.com/products/assistant/settings)中配置助手：

* **示例问题**：添加常见问题，例如“如何提交费用报销单”或“休假政策是什么”，以便用户可以一键获得答案。
* **搜索站点**：添加助手在回答问题时可以搜索的其他网站。
* **分流邮箱**：为助手无法回答的问题设置一个支持邮箱地址。

<div id="add-the-assistant-to-slack">
  ### 将助手添加到 Slack
</div>

[Slack 机器人](/zh/ai/slack-bot) 让你的团队无需离开 Slack 就能向助手提问。你可以创建一个频道，让机器人回复每一条消息，或者让大家在任何频道中 @提及 该机器人来提问。

<div id="enable-team-contributions">
  ## 启用团队协作
</div>

当不仅是最初搭建知识库的人，而是团队中的每一位成员都能参与更新时，知识库才能保持准确。Mintlify 提供三种方式，帮助团队成员快速为你的知识库做出贡献。

<div id="web-editor">
  ### Web 编辑器
</div>

[Web 编辑器](/zh/editor) 让任何人都可以在浏览器中创建和编辑页面。贡献者可以：

* 以可视化方式或使用 Markdown 编辑页面。
* 通过拖放来重新组织导航结构。
* 上传图片和媒体。
* 创建分支和拉取请求（pull request）以供审阅。

这非常适合那些了解内容但不熟悉代码流程的领域专家。

<div id="agent">
  ### Agent
</div>

仪表盘中的 [agent](/zh/agent/quickstart) 可以根据自然语言指令创建文档更新。你只需描述想要修改的内容，agent 就会生成包含更新内容的 pull request。

例如，某位团队成员可以这样提示：“在报销政策页面添加一个部分，解释如何提交超过 50 美元的餐饮报销收据”，并将现有的报销政策页面复制到提示中。agent 会起草相关内容并打开一个 PR 供审核。

<div id="capture-knowledge-from-slack">
  ### 从 Slack 捕获知识
</div>

团队会在 Slack 中分享大量有价值的信息，但这些信息往往不会被整理进文档。[Slack 中的 agent](/zh/agent/slack) 可以捕获这些知识，并将其转换为结构化文档。

当有人在 Slack 线程中分享了有用信息时，任何团队成员都可以 @ 提到 `@mintlify`，并附上将其文档化的指令。agent 会读取对话内容，提取相关信息，并创建一个 pull request。这对于在上下文还记忆犹新时记录技术决策、故障排除方案和流程说明非常有用。

例如，如果你的团队在某个线程中讨论了如何配置一个新的集成，你可以回复：

> @mintlify 基于这次对话创建一份关于配置 Acme 集成的指南。

agent 会利用该线程的上下文来创建文档，从讨论中捕获关键信息。

<div id="locally">
  ### 本地
</div>

任何有权访问你的知识库仓库的人，都可以在本地使用自己喜欢的编辑器进行操作，并将更改推送到仓库。

<div id="establish-maintenance-workflows">
  ## 建立维护工作流程
</div>

如果缺乏维护，知识库会很快变得陈旧、过时。建立相应机制来保持内容及时更新，并帮助你的团队持续为知识库做出贡献。

<Steps>
  <Step title="分配内容所有权">
    为每个部分指定一名负责人或一个小团队。他们不必亲自撰写所有内容，但需要负责：

    * 定期审查内容。
    * 标记过时的信息。
    * 审批其负责部分中的新页面。
    * 在有人报告错误时及时响应。
  </Step>

  <Step title="设置审查周期和内容验证">
    内容会随着时间推移而变得陈旧。制定一个审查计划。

    * **关键内容**：每 30 天审查一次
    * **标准内容**：每 90 天审查一次
    * **常青内容**：每年审查一次

    审查时，请检查：

    * 链接是否仍然有效？
    * 系统或流程是否发生了变化？
    * 示例是否是最新的？
    * 是否有新的信息需要补充？
  </Step>

  <Step title="制定贡献指南">
    让任何人都能轻松改进知识库。你的指南应涵盖：

    * **格式**：你是否有特定的模板或格式要求？
    * **流程**：别人应如何提出并提交修改？
    * **审查**：由谁来审查提交内容？通常的处理时间是多久？
    * **范围**：哪些类型的内容属于适用范围？
  </Step>

  <Step title="监控使用指标">
    审查团队如何使用知识库，以便为内容排定优先级并识别可改进的方向。设定固定频率来查看使用指标——每月或每季度都是不错的选择。

    * 哪些文章浏览量最高？应投入更多精力保持这些内容的准确性和易读性。
    * 哪些文章几乎没有浏览量？可以考虑删除它们，或提升其可发现性。
    * 跳出率如何？如果人们立即离开，内容可能不够有用，或者导航方式有待改进。
  </Step>
</Steps>

<div id="next-steps">
  ## 后续步骤
</div>

你的知识库已经准备就绪，可以上线。部署之后：

1. 通知团队知识库已上线。
2. 在分析工具中监控使用情况和搜索行为。
3. 当有人发现内容空缺时，鼓励他们补充内容。
4. 定期审查并更新内容。

最成功的知识库都会根据团队的实际使用方式不断演进。
