Git 是一种版本控制系统，用于跟踪文档的更改并支持团队协作。使用 Git，你可以查看文件在一段时间内发生了哪些更改、是谁做的、更改发生在何时，以及更改的原因。如果需要撤销更改，Git 还能让你轻松回退到文件的先前版本。

Web 编辑器会在后台执行 Git 操作。如果了解 Git，你就能更高效地使用 Web 编辑器，并与使用本地开发环境的团队成员协同工作。

<div id="why-git-for-documentation">
  ## 为什么用 Git 管理文档？
</div>

Git 提供了管理文档所需的关键功能。

* **版本历史**：查看每个文件在何时、因何原因发生了哪些更改。
* **协作**：多个人可以同时处理文档的不同部分。
* **安全性**：可以放心试验，而不会破坏线上文档。
* **审查流程**：团队成员可以在发布前审阅更改。
* **恢复**：撤销错误操作或还原到先前版本。

<div id="new-to-git">
  ## 初次使用 Git？
</div>

如果你对 Git 和版本控制完全陌生，可以按照这条学习路径开始上手。

<Steps>
  <Step title="先使用网页版编辑器。">
    [网页版编辑器](/zh/editor/index) 会自动处理 Git 操作。

    * 在修改时直观地看到每一处变更。
    * 一键创建分支。
    * 无需使用 Git 命令即可发布并创建 pull request。

    这样你就可以在不使用命令行的情况下理解和掌握 Git 概念。
  </Step>

  <Step title="通过实践来学习。">
    当你使用网页版编辑器时，你就在实际使用 Git。

    * **Save changes** 会创建一个 commit。
    * **Create branch** 会创建一个 Git 分支。
    * **Publish** 会打开一个 pull request 供审核。
  </Step>

  <Step title="在需要时再探索本地开发。">
    你可以完全通过网页版编辑器和仪表板管理你的文档，但也可以在本地环境中工作来自定义工作流。

    * 在你喜欢的编辑器中创建和编辑文件。
    * 使用命令行 Git、GitHub Desktop，或编辑器中的扩展。
    * 在发布前本地预览更改。
    * 集成其他工具，如客服工单、问题跟踪和设计系统。
  </Step>
</Steps>

<div id="core-git-concepts">
  ## 核心 Git 概念
</div>

<AccordionGroup>
  <Accordion title="分支">
    分支指向仓库中的某个特定提交。你的在线文档是从部署分支构建的。你可以有任意数量的其他分支，这些分支上的更改尚未发布到在线文档。如果你想把某个分支中的更改合并到在线文档中，可以通过拉取请求将该分支合并到部署分支。

    使用分支可以在不影响在线文档的情况下进行更改、安全地尝试新功能，并在发布前获取审阅反馈。
  </Accordion>

  <Accordion title="克隆">
    将仓库的完整副本下载到你的电脑上，包括所有文件及其完整历史。克隆后，你会获得在本地工作的所有必需内容。

    ```bash
    git clone https://github.com/your-org/your-repo
    ```
  </Accordion>

  <Accordion title="提交">
    在某个特定时间点保存的更改快照。每次提交都会包含一条描述发生了哪些更改的消息，并在项目历史中创建一条永久记录。
  </Accordion>

  <Accordion title="冲突">
    当两个人以不同方式修改了同一文件的同一部分时就会发生冲突。Git 会要求你手动选择保留哪一方的更改，或将两者合并。
  </Accordion>

  <Accordion title="部署分支">
    项目的主分支。对该分支的更改会自动发布到你的文档站点。通常叫作 `main`，但你可以将任意分支设置为部署分支。
  </Accordion>

  <Accordion title="Diff">
    diff（差异）展示的是文件两个版本之间的更改。在审阅拉取请求时，diff 会高亮显示与文件原始版本的不同之处。
  </Accordion>

  <Accordion title="合并">
    将一个分支中的更改合入另一个分支。通常在审阅之后，通过拉取请求完成合并，将功能开发工作纳入部署分支。
  </Accordion>

  <Accordion title="拉取">
    从远程仓库获取最新更改到本地副本，帮助你与他人的工作保持同步。

    ```bash
    git pull
    ```
  </Accordion>

  <Accordion title="拉取请求">
    一种将某个分支上的更改提议合并进在线文档的方式。它允许在更改上线前进行审阅和讨论。通常称为 PR，在 GitLab 中也被称为合并请求（merge request）。
  </Accordion>

  <Accordion title="推送">
    将本地提交发送到远程仓库。这样会让你的更改对他人可见，并可能触发自动部署。

    ```bash
    git push
    ```
  </Accordion>

  <Accordion title="远程仓库">
    托管在服务器上的仓库版本。本地仓库通过连接远程仓库来推送和拉取更改。
  </Accordion>

  <Accordion title="仓库">
    你的文档站点所用的源代码，包括构成文档页面的所有文件及其历史记录。网页编辑器会连接到你的文档仓库以访问和修改内容。
  </Accordion>

  <Accordion title="暂存">
    准备好要包含在下一个提交中的特定更改。暂存可以帮助你将更改组织成逻辑清晰的提交。

    ```bash
    git add filename.mdx
    ```
  </Accordion>
</AccordionGroup>

<div id="how-the-web-editor-uses-git">
  ## Web 编辑器如何使用 Git
</div>

Web 编辑器通过 [GitHub App](/zh/deploy/github) 或 [GitLab 集成](/zh/deploy/gitlab) 连接到你的 Git 仓库，并自动执行常见的 Git 操作。

当你：

* **打开文件**：编辑器会从仓库中获取最新版本，确保你始终在编辑最新的内容。
* **进行修改**：编辑器会将你的更改记录为草稿，当你准备好保存工作时，可以将其变成一次 commit。
* **保存更改**：编辑器会基于你的更改创建一次 commit，将你的工作保存在项目历史中。
* **创建分支**：编辑器会在仓库中创建一个新分支，任何有仓库访问权限的人都可以在该分支上协作并审阅更改。
* **发布到部署分支**：编辑器会直接向你的部署分支提交并推送，从而立即发布你的更改。
* **发布到其他分支**：编辑器会创建一个 pull request，使你可以在将更改合并到部署分支之前获得他人的反馈。

<div id="common-workflows">
  ## 常见工作流程
</div>

<div id="publish-directly-to-your-deployment-branch">
  ### 直接发布到你的部署分支
</div>

<Tabs>
  <Tab title="使用在线编辑器">
    1. 在[在线编辑器](https://dashboard.mintlify.com/editor)中打开文件。
    2. 修改内容。
    3. 点击 **Publish**。
    4. 修改会出现在代码仓库中并自动部署。
  </Tab>

  <Tab title="使用本地开发">
    1. 拉取最新更新：`git pull`
    2. 在本地编辑器中编辑文件。
    3. 暂存修改：`git add filename.mdx`
    4. 提交：`git commit -m "Update documentation"`
    5. 推送：`git push`
    6. 修改会自动部署。
  </Tab>
</Tabs>

<div id="work-on-a-feature-branch">
  ### 在功能分支中进行开发
</div>

<Tabs>
  <Tab title="使用网页编辑器">
    <Note>
      要在网页编辑器中创建 pull request，你必须启用分支保护规则，并要求在更改合并到部署分支之前先通过 pull request 审核。没有分支保护规则时，分支上的更改在发布时会直接合并到部署分支。
    </Note>

    1. 在编辑器工具栏的分支下拉列表中创建分支。
    2. 在该分支上进行更改并保存。
    3. 点击 **Publish** 以创建 pull request。
    4. 准备就绪后合并该 pull request。
  </Tab>

  <Tab title="使用本地开发环境">
    1. 创建分支：`git checkout -b feature-name`
    2. 进行更改并提交。
    3. 推送分支：`git push -u origin feature-name`
    4. 创建一个 pull request。
    5. 准备就绪后合并该 pull request。
  </Tab>
</Tabs>

<div id="review-changes-before-publishing">
  ### 在发布前审查更改
</div>

<Steps>
  <Step title="创建功能分支。">
    在独立于部署分支的分支上进行更改，这样你可以在发布前共享并审查这些更改。
  </Step>

  <Step title="进行更改。">
    编辑文件并将更改提交到功能分支。
  </Step>

  <Step title="创建拉取请求。">
    创建拉取请求，提议将功能分支上的更改合并到部署分支。
  </Step>

  <Step title="审查差异。">
    检查你的更改。拉取请求会逐行显示文件与原始版本之间的差异。
  </Step>

  <Step title="获取团队反馈。">
    团队成员可以针对特定行或整体更改发表评论。根据反馈进行修改并提交到功能分支。
  </Step>

  <Step title="批准后合并。">
    合并拉取请求，将更改发布到线上文档。
  </Step>
</Steps>

<div id="git-best-practices">
  ## Git 最佳实践
</div>

每个团队都会形成自己的工作流程和偏好，但以下是一些通用的最佳实践，方便你入门。

* **编写清晰具体的提交信息**：用主动语态明确说明改动内容。`Fix broken link in API docs` 比 `update page` 更有信息量。
* **使用具有描述性的分支名称**：分支名应能说明该分支的用途。使用像 `update-api-reference` 这样信息量更大的名字，而不是 `temp` 或 `my-branch` 这类泛泛的名称。
* **让分支聚焦单一目标**：让一个分支上的改动专注于某个特定任务或项目。这有助于简化代码评审并减少冲突。
* **合并后删除分支**：在不再需要某个分支时将其删除，以保持仓库整洁。
* **先拉取再推送**：始终在推送前先拉取最新改动，以避免冲突。网页编辑器会自动帮你完成这一步。
* **先自查自己的改动**：在创建 pull request 之前先检查 diff。
