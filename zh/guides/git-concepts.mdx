Git 是一种版本控制系统，用于跟踪文档变更并支持团队协作。借助 Git，你可以查看文件随着时间推移发生了哪些变化、这些变化由谁做出、何时做出，以及为什么要做这些更改。如果你需要撤销更改，Git 还能让你轻松恢复到文件的早期版本。

网页编辑器会在后台执行 Git 操作。了解 Git 后，你就能更高效地使用网页编辑器，并与采用本地开发方式的团队成员协作。

<div id="why-git-for-documentation">
  ## 为什么文档要用 Git？
</div>

Git 为管理文档提供了必不可少的能力。

* **版本历史**：查看每个文件改了什么、何时修改，以及为什么修改。
* **协作**：多人可以同时处理不同部分的内容。
* **安全性**：可以放心试验，而不会影响在线文档。
* **审查工作流**：团队成员可以在发布前审查变更。
* **恢复**：撤销错误或恢复到之前的版本。

<div id="new-to-git">
  ## 刚开始接触 Git？
</div>

如果你完全不熟悉 Git 和版本控制，可以按下面的路径开始上手。

<Steps>
  <Step title="先使用网页编辑器。">
    [网页编辑器](/zh/editor/index)会自动处理 Git 操作。

    * 你在修改时，可以直观地看到所有变更。
    * 一键创建分支。
    * 无需使用 Git 命令即可发布并创建拉取请求。

    这样一来，你无需使用命令行也能理解 Git 的核心概念。
  </Step>

  <Step title="边做边学。">
    当你使用网页编辑器时，其实就是在使用 Git。

    * **Save changes** 会创建一次提交。
    * **Create branch** 会创建一个 Git 分支。
    * **Publish** 会发起一个拉取请求供审核。
  </Step>

  <Step title="在需要时再尝试本地开发。">
    你可以完全通过网页编辑器和仪表板来管理文档，但如果想进一步自定义工作流程，也可以在本地环境中进行。

    * 在你常用的编辑器中创建和编辑文件。
    * 使用命令行 Git、GitHub Desktop，或编辑器中的扩展。
    * 在发布前先在本地预览变更。
    * 与支持工单、问题跟踪和设计系统等其他工具集成。
  </Step>
</Steps>

<div id="core-git-concepts">
  ## Git 核心概念
</div>

<AccordionGroup>
  <Accordion title="分支">
    分支指向仓库中的某个特定提交。你的在线文档会基于部署分支构建。你还可以创建任意数量的其他分支，用来保存尚未发布到在线文档的更改。如果你想把某个分支中的更改纳入在线文档，可以通过拉取请求将该分支合并到部署分支。

    使用分支可以在不影响在线文档的情况下处理更改、安全试验新功能，并在发布前获得审核。
  </Accordion>

  <Accordion title="克隆">
    将仓库的完整副本下载到你的计算机中，包括所有文件和完整历史记录。克隆后，你就拥有了在本地开展工作所需的全部内容。

    ```bash
    git clone https://github.com/your-org/your-repo
    ```
  </Accordion>

  <Accordion title="提交">
    在某个特定时间点保存的更改快照。每次提交都包含一条说明更改内容的消息，并会在项目历史中留下永久记录。
  </Accordion>

  <Accordion title="冲突">
    当两个人以不同方式修改了文件的同一部分时，就会发生冲突。Git 会要求你手动选择保留哪项更改，或将两项更改合并起来。
  </Accordion>

  <Accordion title="部署分支">
    项目的主分支。对此分支的更改会自动发布到你的文档站点。它通常叫做 `main`，但你也可以将任意分支设为部署分支。
  </Accordion>

  <Accordion title="差异">
    差异 (即 difference) 显示文件两个版本之间的差异。在审核拉取请求时，差异会突出显示与文件原始版本不同的内容。
  </Accordion>

  <Accordion title="合并">
    将一个分支中的更改合并到另一个分支。通常是在审核后通过拉取请求完成，以便将功能开发的成果纳入部署分支。
  </Accordion>

  <Accordion title="拉取">
    将远程仓库中的最新更改获取到本地副本。这样可以让你及时同步其他人的工作。

    ```bash
    git pull
    ```
  </Accordion>

  <Accordion title="拉取请求">
    一种提议将你在某个分支上的更改合并到在线文档中的方式。它支持在更改上线前进行审核和讨论。通常简称为 PR，在 GitLab 中也叫合并请求。
  </Accordion>

  <Accordion title="推送">
    将你的本地提交发送到远程仓库。这会让其他人能够获取你的更改，也可能触发自动部署。

    ```bash
    git push
    ```
  </Accordion>

  <Accordion title="远程仓库">
    托管在服务器上的仓库版本。你的本地仓库会连接到远程仓库，以便推送和拉取更改。
  </Accordion>

  <Accordion title="仓库">
    构成文档站点页面的文档源代码，以及所有相关文件和它们的历史记录。网页编辑器会连接到你的文档仓库，以访问和修改内容。
  </Accordion>

  <Accordion title="暂存">
    准备将特定更改加入下一次提交。暂存可以帮助你将更改组织成逻辑清晰的提交。

    ```bash
    git add filename.mdx
    ```
  </Accordion>
</AccordionGroup>

<div id="how-the-web-editor-uses-git">
  ## 网页编辑器如何使用 Git
</div>

网页编辑器通过 [GitHub App](/zh/deploy/github) 或 [GitLab 集成](/zh/deploy/gitlab) 连接到你的 Git 仓库，并自动完成常见的 Git 操作。

当你：

* **打开文件**：编辑器会从仓库拉取最新版本，确保你始终处理的是最新内容。
* **进行更改**：编辑器会将你的更改保存为草稿，等你准备好保存工作时，再将其转换为一次提交。
* **保存更改**：编辑器会将你的更改提交到项目历史中，保留你的工作记录。
* **创建分支**：编辑器会在你的仓库中创建一个新分支，任何有仓库访问权限的人都可以基于该分支协作并审查更改。
* **在部署分支上发布**：编辑器会直接提交并推送到你的部署分支，立即发布你的更改。
* **在其他分支上发布**：编辑器会创建一个拉取请求，让你在将更改合并到部署分支之前先获得他人的反馈。

<div id="common-workflows">
  ## 常见工作流程
</div>

<div id="publish-directly-to-your-deployment-branch">
  ### 直接发布到部署分支
</div>

<Tabs>
  <Tab title="使用网页编辑器">
    1. 在[网页编辑器](https://dashboard.mintlify.com/editor)中打开文件。
    2. 进行修改。
    3. 点击**发布**。
    4. 更改会显示在仓库中，并自动部署。
  </Tab>

  <Tab title="使用本地开发">
    1. 拉取最新更改：`git pull`
    2. 在编辑器中编辑文件。
    3. 暂存更改：`git add filename.mdx`
    4. 提交：`git commit -m "Update documentation"`
    5. 推送：`git push`
    6. 更改会自动部署。
  </Tab>
</Tabs>

<div id="work-on-a-feature-branch">
  ### 在功能分支上进行开发
</div>

<Tabs>
  <Tab title="使用网页编辑器">
    <Note>
      如需通过网页编辑器创建拉取请求，你必须启用分支保护规则，要求更改在合并到部署分支前先通过拉取请求。若未启用分支保护规则，分支上的更改会在发布时直接合并到部署分支。
    </Note>

    1. 在编辑器工具栏的分支下拉菜单中创建分支。
    2. 在该分支上进行更改并保存。
    3. 点击 **发布** 以创建拉取请求。
    4. 准备就绪后，合并拉取请求。
  </Tab>

  <Tab title="使用本地开发">
    1. 创建分支：`git checkout -b feature-name`
    2. 进行更改并提交。
    3. 推送分支：`git push -u origin feature-name`
    4. 创建拉取请求。
    5. 准备就绪后，合并拉取请求。
  </Tab>
</Tabs>

<div id="review-changes-before-publishing">
  ### 发布前先检查更改
</div>

<Steps>
  <Step title="创建功能分支。">
    在独立于部署分支的分支中进行更改，以便你在发布前共享并审查这些更改。
  </Step>

  <Step title="进行更改。">
    编辑文件，并将更改提交到功能分支。
  </Step>

  <Step title="创建拉取请求。">
    创建拉取请求，提议将功能分支中的更改合并到部署分支。
  </Step>

  <Step title="查看差异。">
    检查你的更改。拉取请求会显示文件相对于原始版本的逐行差异。
  </Step>

  <Step title="获取团队反馈。">
    团队成员可以对具体行或整体更改发表评论。根据反馈进行修改，并将其提交到功能分支。
  </Step>

  <Step title="获批后合并。">
    合并拉取请求，将更改发布到你的在线文档。
  </Step>
</Steps>

<div id="git-best-practices">
  ## Git 最佳实践
</div>

每个团队都会形成自己的工作流程和偏好，不过你可以先从以下这些通用最佳实践开始。

* **编写清晰的提交信息**：用明确、主动的表述说明改了什么。`Fix broken link in API docs` 比 `update page` 信息更充分。
* **使用有意义的分支名称**：分支名称应说明这个分支的用途。尽量使用像 `update-api-reference` 这样含义明确的名称，而不要用 `temp` 或 `my-branch` 这类泛泛的名字。
* **保持分支聚焦**：让一个分支中的改动围绕单一任务或项目展开。这样更便于审查，也能减少冲突。
* **合并后删除分支**：分支不再需要时就删除，以保持仓库整洁。
* **推送前先拉取**：推送前务必先拉取最新更改，避免发生冲突。网页编辑器会自动执行此操作。
* **先检查自己的更改**：在创建拉取请求之前，先查看差异。
