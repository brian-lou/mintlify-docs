<Tip>
  本页介绍了从自动化检查到内容生命周期等策略，帮助你长期保持文档的准确性和价值。
</Tip>

<div id="automate-what-you-can">
  ## 尽可能自动化
</div>

在力所能及的地方引入自动化，例如：

* **跟踪陈旧内容：** 运行脚本标记过去三个月内没有更新的重要文档。它们是否仍然准确？
* **自动化文档更新：** 构建一个工作流程，在代码与 [agent API](/zh/guides/automate-agent) 合并时自动更新文档。
* **用 linter 执行规范：** 使用 [Vale](http://Vale.sh) 或 [CI checks](/zh/deploy/ci)，在每次 pull request 中自动发现格式问题、写作风格偏差或缺失的元数据。

<div id="set-up-a-review-process">
  ## 建立评审流程
</div>

文档可能永远无法做到完美，这没关系。你应该设定一个可接受的标准，只要文档是可用且有用的就行。

在效率与质量之间寻找平衡：

* **专注于高影响力文档。** 并不是每个页面都需要定期更新。要确保最重要的页面能定期审查其准确性和相关性。
* **善用你的社区。** 如果你的文档是开源的，可以让用户通过 pull request 标记问题或提交修复。这有助于建立信任，并让内容保持最新。

<div id="know-when-to-rewrite">
  ## 要知道何时该重写
</div>

随着时间推移，文档自然会积累各种注意事项和变通方案。当后续的修修补补带来的困惑多于清晰时，全面重做可能是更好的选择。

* **规划定期“重置”。** 进行一次大规模清理，尤其是在最佳实践或产品本身已经发生显著变化的情况下，可以为你的团队和用户节省时间。
* **从结构化审查开始。** 访谈支持团队、分析用户反馈，并在重写前记录哪些内容缺失、易引起误解或属于冗余。
* **在集中迭代中完成彻底重写。** 全面重做不必一次性完成。优先处理影响最大的部分。

<div id="wrong-docs-can-be-worse-than-no-docs">
  ## 错误的文档往往比没有文档更糟糕
</div>

过时或具有误导性的文档会浪费用户时间并削弱信任。在某些情况下，如果某个页面完全不准确且在短期内无法修复，通常最好直接将其删除。与其看到错误的信息，用户更希望哪怕信息少一些也要保证正确。
