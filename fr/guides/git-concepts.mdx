Git est un système de gestion de versions qui suit les modifications apportées à votre documentation et permet la collaboration au sein de votre équipe. Avec Git, vous pouvez voir ce qui a changé dans vos fichiers au fil du temps, qui a effectué les modifications, quand elles ont été faites et pourquoi. Git facilite également le retour à des versions précédentes des fichiers si vous devez annuler des modifications.

L’éditeur web effectue des opérations Git en arrière-plan. En comprenant Git, vous pouvez travailler plus efficacement avec l’éditeur web et collaborer avec les membres de votre équipe qui utilisent un environnement de développement local.

<div id="why-git-for-documentation">
  ## Pourquoi Git pour la documentation ?
</div>

Git offre des fonctionnalités essentielles pour gérer la documentation.

* **Historique des versions** : Consulter ce qui a changé, quand et pourquoi pour chaque fichier.
* **Collaboration** : Plusieurs personnes peuvent travailler simultanément sur différentes parties.
* **Sécurité** : Faire des essais sans casser la documentation en production.
* **Workflows de relecture** : Les membres de l’équipe peuvent relire les changements avant la publication.
* **Récupération** : Annuler des erreurs ou restaurer des versions précédentes.

<div id="new-to-git">
  ## Nouveau sur Git ?
</div>

Si vous découvrez Git et la gestion de versions, voici un parcours pour vous lancer.

<Steps>
  <Step title="Utilisez d’abord l’éditeur web.">
    L’[éditeur web](/fr/editor/index) gère automatiquement les opérations Git.

    * Visualisez instantanément toutes les modifications au fur et à mesure que vous les effectuez.
    * Créez des branches en un clic.
    * Publiez et créez des pull requests sans utiliser de commandes Git.

    Cela vous permet d’apprendre les concepts de Git sans utiliser la ligne de commande.
  </Step>

  <Step title="Apprenez en pratiquant.">
    Lorsque vous utilisez l’éditeur web, vous utilisez Git.

    * **Save changes** crée un commit.
    * **Create branch** crée une branche Git.
    * **Publish** ouvre une pull request pour relecture.
  </Step>

  <Step title="Explorez le développement local quand cela devient utile.">
    Vous pouvez gérer votre documentation entièrement avec l’éditeur web et le tableau de bord, mais vous pouvez aussi personnaliser votre flux de travail en travaillant dans votre environnement local.

    * Créez et modifiez des fichiers dans votre éditeur préféré.
    * Utilisez Git en ligne de commande, GitHub Desktop ou une extension dans votre éditeur.
    * Prévisualisez les modifications en local avant de les publier.
    * Intégrez d’autres outils comme les tickets de support, le suivi des incidents et les design systems.
  </Step>
</Steps>

<div id="core-git-concepts">
  ## Concepts Git essentiels
</div>

<AccordionGroup>
  <Accordion title="Branche">
    Une branche pointe vers un commit spécifique dans votre dépôt. Votre documentation en ligne est construite à partir d&#39;une branche de déploiement. Vous pouvez avoir un nombre quelconque d&#39;autres branches contenant des modifications qui ne sont pas encore publiées dans votre documentation en ligne. Si vous souhaitez intégrer les modifications d&#39;une branche dans votre documentation en ligne, vous pouvez fusionner cette branche dans votre branche de déploiement via une pull request.

    Utilisez les branches pour travailler sur des modifications sans affecter votre documentation en ligne, expérimenter en toute sécurité de nouvelles fonctionnalités et obtenir des revues avant la publication.
  </Accordion>

  <Accordion title="Clone">
    Téléchargez une copie complète d&#39;un dépôt sur votre ordinateur, y compris tous les fichiers et l&#39;historique complet. Quand vous clonez, vous obtenez tout ce dont vous avez besoin pour travailler en local.

    ```bash
    git clone https://github.com/your-org/your-repo
    ```
  </Accordion>

  <Accordion title="Commit">
    Une capture enregistrée de vos modifications à un moment précis. Chaque commit inclut un message décrivant ce qui a changé et crée un enregistrement permanent dans l&#39;historique de votre projet.
  </Accordion>

  <Accordion title="Conflit">
    Se produit lorsque deux personnes modifient différemment la même partie d&#39;un fichier. Git vous demande de choisir manuellement quelle modification conserver ou de combiner les deux.
  </Accordion>

  <Accordion title="Branche de déploiement">
    La branche principale de votre projet. Les modifications apportées à cette branche sont automatiquement publiées sur votre site de documentation. Souvent appelée `main`, mais vous pouvez définir n&#39;importe quelle branche comme branche de déploiement.
  </Accordion>

  <Accordion title="Diff">
    Un diff (ou différence) montre les modifications entre deux versions d&#39;un fichier. Lors de la revue de pull requests, les diffs mettent en évidence ce qui est différent par rapport à la version originale du fichier.
  </Accordion>

  <Accordion title="Merge">
    Combiner les modifications d&#39;une branche dans une autre. Généralement effectué via une pull request après revue, pour intégrer un travail de fonctionnalité dans votre branche de déploiement.
  </Accordion>

  <Accordion title="Pull">
    Récupérez les dernières modifications depuis le dépôt distant vers votre copie locale. Cela vous permet de rester à jour avec le travail des autres.

    ```bash
    git pull
    ```
  </Accordion>

  <Accordion title="Pull request">
    Une façon de proposer la fusion de vos modifications d&#39;une branche dans votre documentation en ligne. Permet la revue et la discussion avant que les modifications ne soient mises en ligne. Couramment appelée PR, et aussi appelée merge request dans GitLab.
  </Accordion>

  <Accordion title="Push">
    Envoyez vos commits locaux vers le dépôt distant. Cela rend vos modifications disponibles pour les autres et peut déclencher des déploiements automatiques.

    ```bash
    git push
    ```
  </Accordion>

  <Accordion title="Dépôt distant">
    Une version de votre dépôt hébergée sur un serveur. Votre dépôt local se connecte à un dépôt distant pour envoyer et récupérer des modifications.
  </Accordion>

  <Accordion title="Dépôt">
    Le code source de votre documentation avec tous les fichiers, et leur historique, qui constituent les pages de votre site de documentation. L&#39;éditeur web se connecte à votre dépôt de documentation pour accéder au contenu et le modifier.
  </Accordion>

  <Accordion title="Indexation (stage)">
    Indexez des modifications spécifiques à inclure dans votre prochain commit. L’indexation vous permet d&#39;organiser les modifications en commits logiques.

    ```bash
    git add filename.mdx
    ```
  </Accordion>
</AccordionGroup>

<div id="how-the-web-editor-uses-git">
  ## Comment l&#39;éditeur web utilise Git
</div>

L&#39;éditeur web se connecte à votre dépôt Git via l&#39;[application GitHub](/fr/deploy/github) ou l&#39;[intégration GitLab](/fr/deploy/gitlab) et automatise les opérations Git courantes.

Lorsque vous :

* **Ouvrez un fichier** : l&#39;éditeur récupère la dernière version depuis votre dépôt, ce qui garantit que vous travaillez toujours avec un contenu à jour.
* **Apportez des modifications** : l&#39;éditeur suit vos modifications comme un brouillon qui pourra devenir un commit lorsque vous serez prêt à enregistrer votre travail.
* **Enregistrez les modifications** : l&#39;éditeur crée un commit avec vos modifications, en préservant votre travail dans l&#39;historique du projet.
* **Créez une branche** : l&#39;éditeur crée une nouvelle branche dans votre dépôt que toute personne ayant accès au dépôt peut utiliser pour collaborer et examiner les modifications.
* **Publiez sur votre branche de déploiement** : l&#39;éditeur crée un commit et envoie directement vos modifications sur votre branche de déploiement, ce qui les publie immédiatement.
* **Publiez sur d&#39;autres branches** : l&#39;éditeur crée une pull request, ce qui vous permet d&#39;obtenir des retours d&#39;autres personnes avant de fusionner vos modifications dans votre branche de déploiement.

<div id="common-workflows">
  ## Workflows courants
</div>

<div id="publish-directly-to-your-deployment-branch">
  ### Publier directement sur votre branche de déploiement
</div>

<Tabs>
  <Tab title="Utiliser l'éditeur en ligne">
    1. Ouvrez le fichier dans l&#39;[éditeur en ligne](https://dashboard.mintlify.com/editor).
    2. Apportez vos modifications.
    3. Cliquez sur **Publish**.
    4. Les modifications apparaissent dans le dépôt et sont déployées automatiquement.
  </Tab>

  <Tab title="Utiliser un environnement de développement local">
    1. Récupérez les dernières modifications : `git pull`
    2. Modifiez le fichier dans votre éditeur.
    3. Préparez les modifications : `git add filename.mdx`
    4. Validez les modifications : `git commit -m "Update documentation"`
    5. Envoyez les modifications : `git push`
    6. Les modifications sont déployées automatiquement.
  </Tab>
</Tabs>

<div id="work-on-a-feature-branch">
  ### Travailler sur une branche de fonctionnalité
</div>

<Tabs>
  <Tab title="Utilisation de l’éditeur web">
    <Note>
      Pour créer des pull requests à partir de l’éditeur web, vous devez avoir une règle de protection de branche active qui impose de passer par des pull requests avant que les modifications puissent être fusionnées dans votre branche de déploiement. Sans règles de protection de branche, les modifications sur les branches sont fusionnées dans votre branche de déploiement lors de la publication.
    </Note>

    1. Créez une branche à partir du menu déroulant des branches dans la barre d’outils de l’éditeur.
    2. Effectuez et enregistrez vos modifications sur la branche.
    3. Cliquez sur **Publish** pour créer une pull request.
    4. Fusionnez la pull request lorsque vous êtes prêt.
  </Tab>

  <Tab title="Utilisation du développement local">
    1. Créez une branche : `git checkout -b feature-name`
    2. Effectuez et validez vos modifications.
    3. Poussez la branche : `git push -u origin feature-name`
    4. Créez une pull request.
    5. Fusionnez la pull request lorsque vous êtes prêt.
  </Tab>
</Tabs>

<div id="review-changes-before-publishing">
  ### Examiner les modifications avant la publication
</div>

<Steps>
  <Step title="Créer une branche de fonctionnalité.">
    Travaillez sur vos modifications dans une branche distincte de votre branche de déploiement afin de pouvoir les partager et les examiner avant de les publier.
  </Step>

  <Step title="Apporter vos modifications.">
    Modifiez les fichiers et validez les modifications dans la branche de fonctionnalité.
  </Step>

  <Step title="Créer une pull request.">
    Créez une pull request pour proposer la fusion des modifications de votre branche de fonctionnalité dans la branche de déploiement.
  </Step>

  <Step title="Examiner le diff.">
    Vérifiez vos modifications. La pull request affiche, ligne par ligne, les différences par rapport à la version d’origine du fichier.
  </Step>

  <Step title="Obtenir les retours de l’équipe.">
    Les membres de l’équipe peuvent commenter des lignes précises ou l’ensemble des modifications. Apportez les changements nécessaires et validez-les dans la branche de fonctionnalité.
  </Step>

  <Step title="Fusionner après approbation.">
    Fusionnez la pull request pour publier les modifications dans votre documentation en production.
  </Step>
</Steps>

<div id="git-best-practices">
  ## Bonnes pratiques Git
</div>

Chaque équipe développe ses propres workflows et préférences, mais voici quelques bonnes pratiques générales pour commencer.

* **Rédigez des messages de commit descriptifs** : soyez précis sur ce qui a changé en utilisant un langage actif. `Fix broken link in API docs` est plus informatif que `update page`.
* **Utilisez des noms de branches descriptifs** : les noms de branches doivent expliquer l’objectif de la branche. Utilisez des noms explicites comme `update-api-reference` plutôt que des noms génériques comme `temp` ou `my-branch`.
* **Gardez les branches focalisées** : limitez les changements sur une branche à une tâche ou un projet spécifique. Cela facilite les revues de code et réduit les conflits.
* **Supprimez les branches après les avoir fusionnées** : supprimez les branches lorsque vous n’en avez plus besoin afin de garder votre dépôt propre.
* **Faites un pull avant de pousser** : récupérez toujours les derniers changements avant de pousser afin d’éviter les conflits. L’éditeur web le fait automatiquement.
* **Relisez d’abord vos propres changements** : vérifiez le diff avant de créer une pull request.
