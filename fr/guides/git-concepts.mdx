Git est un système de contrôle de version qui suit les modifications apportées à votre documentation et facilite la collaboration en équipe. Avec Git, vous pouvez voir ce qui a changé au fil du temps dans les fichiers, qui a apporté les modifications, quand elles ont été effectuées et pourquoi. Git permet également de revenir facilement à des versions antérieures des fichiers si vous devez annuler des modifications.

L’éditeur web effectue les opérations Git en arrière-plan. En comprenant Git, vous pouvez travailler plus efficacement avec l’éditeur web et collaborer avec les membres de l’équipe qui travaillent en local.

<div id="why-git-for-documentation">
  ## Pourquoi Git pour la documentation ?
</div>

Git offre des fonctionnalités essentielles pour gérer la documentation.

* **Historique des versions** : voyez ce qui a changé, quand et pourquoi, pour chaque fichier.
* **Collaboration** : plusieurs personnes peuvent travailler simultanément sur différentes parties.
* **Sécurité** : expérimentez sans risquer de compromettre la documentation en ligne.
* **Processus de révision** : les membres de l’équipe peuvent relire les modifications avant leur publication.
* **Restauration** : corrigez les erreurs ou revenez à des versions antérieures.

<div id="new-to-git">
  ## Vous débutez avec Git ?
</div>

Si vous découvrez totalement Git et le contrôle de version, voici une bonne façon de commencer.

<Steps>
  <Step title="Commencez par l'éditeur web.">
    L&#39;[éditeur web](/fr/editor/index) gère automatiquement les opérations Git.

    * Visualisez chaque modification au fur et à mesure.
    * Créez des branches en un clic.
    * Publiez et créez des pull requests sans utiliser de commandes Git.

    Cela vous permet d&#39;assimiler les concepts de Git sans passer par la ligne de commande.
  </Step>

  <Step title="Apprenez en faisant.">
    Quand vous utilisez l&#39;éditeur web, vous utilisez déjà Git.

    * **Save changes** crée un commit.
    * **Create branch** crée une branche Git.
    * **Publish** ouvre une pull request pour relecture.
  </Step>

  <Step title="Passez au développement local quand c'est utile.">
    Vous pouvez gérer toute votre documentation avec l&#39;éditeur web et le tableau de bord, mais vous pouvez aussi adapter votre workflow en travaillant dans votre environnement local.

    * Créez et modifiez des fichiers dans votre éditeur préféré.
    * Utilisez Git en ligne de commande, GitHub Desktop ou une extension dans votre éditeur.
    * Prévisualisez les modifications en local avant de publier.
    * Intégrez d&#39;autres outils comme les tickets de support, le suivi des problèmes et les design systems.
  </Step>
</Steps>

<div id="core-git-concepts">
  ## Concepts fondamentaux de Git
</div>

<AccordionGroup>
  <Accordion title="Branche">
    Une branche pointe vers un commit précis dans votre dépôt. Votre documentation en ligne est générée à partir d’une branche de déploiement. Vous pouvez avoir autant d’autres branches que vous le souhaitez contenant des modifications qui ne sont pas encore publiées sur votre documentation en ligne. Si vous voulez intégrer les modifications d’une branche à votre documentation en ligne, vous pouvez fusionner cette branche dans votre branche de déploiement via une pull request.

    Utilisez les branches pour travailler sur des modifications sans affecter votre documentation en ligne, tester de nouvelles fonctionnalités en toute sécurité et obtenir des retours avant la publication.
  </Accordion>

  <Accordion title="Clone">
    Téléchargez une copie complète d’un dépôt sur votre ordinateur, y compris tous les fichiers et l’intégralité de son historique. Lorsque vous clonez un dépôt, vous disposez de tout ce qu’il vous faut pour travailler en local.

    ```bash
    git clone https://github.com/your-org/your-repo
    ```
  </Accordion>

  <Accordion title="Commit">
    Un instantané enregistré de vos modifications à un moment donné. Chaque commit inclut un message qui décrit ce qui a changé et crée un enregistrement permanent dans l’historique de votre projet.
  </Accordion>

  <Accordion title="Conflit">
    Se produit lorsque deux personnes modifient différemment la même partie d’un fichier. Git vous demande alors de choisir manuellement quelle modification conserver, ou de combiner les deux.
  </Accordion>

  <Accordion title="Branche de déploiement">
    La branche principale de votre projet. Les modifications apportées à cette branche sont automatiquement publiées sur votre site de documentation. Elle s’appelle souvent `main`, mais vous pouvez définir n’importe quelle branche comme branche de déploiement.
  </Accordion>

  <Accordion title="Diff">
    Un diff (ou différence) montre les modifications entre deux versions d’un fichier. Lors de la révision des pull requests, les diffs mettent en évidence les différences par rapport à la version d’origine du fichier.
  </Accordion>

  <Accordion title="Fusion">
    Combinez les modifications d’une branche dans une autre. Cela se fait généralement via une pull request après révision, afin d’intégrer le travail sur une fonctionnalité à votre branche de déploiement.
  </Accordion>

  <Accordion title="Pull">
    Récupérez les dernières modifications du dépôt distant vers votre copie locale. Cela vous permet de rester à jour avec le travail des autres.

    ```bash
    git pull
    ```
  </Accordion>

  <Accordion title="Pull request">
    Une façon de proposer la fusion des modifications de votre branche dans votre documentation en ligne. Elle permet une révision et une discussion avant la mise en ligne des modifications. On l’appelle couramment PR, et merge request dans GitLab.
  </Accordion>

  <Accordion title="Push">
    Envoyez vos commits locaux vers le dépôt distant. Cela rend vos modifications accessibles aux autres et peut déclencher des déploiements automatiques.

    ```bash
    git push
    ```
  </Accordion>

  <Accordion title="Dépôt distant">
    Une version de votre dépôt hébergée sur un serveur. Votre dépôt local se connecte à un dépôt distant pour envoyer et récupérer des modifications.
  </Accordion>

  <Accordion title="Dépôt">
    Le code source de votre documentation, avec tous les fichiers et leur historique, qui composent les pages de votre site de documentation. L’éditeur web se connecte à votre dépôt de documentation pour accéder au contenu et le modifier.
  </Accordion>

  <Accordion title="Zone de préparation">
    Préparez des modifications précises à inclure dans votre prochain commit. La mise en préparation vous permet d’organiser vos modifications en commits logiques.

    ```bash
    git add filename.mdx
    ```
  </Accordion>
</AccordionGroup>

<div id="how-the-web-editor-uses-git">
  ## Comment l&#39;éditeur web utilise Git
</div>

L&#39;éditeur web se connecte à votre dépôt Git via la [GitHub App](/fr/deploy/github) ou l&#39;[intégration GitLab](/fr/deploy/gitlab) et automatise les opérations Git courantes.

Lorsque vous :

* **Ouvrez un fichier** : l&#39;éditeur récupère la dernière version depuis votre dépôt, afin que vous travailliez toujours sur un contenu à jour.
* **Apportez des modifications** : l&#39;éditeur enregistre vos modifications sous forme de brouillon, qui peut devenir un commit lorsque vous êtes prêt à enregistrer votre travail.
* **Enregistrez les modifications** : l&#39;éditeur crée un commit avec vos modifications, ce qui conserve votre travail dans l&#39;historique du projet.
* **Créez une branche** : l&#39;éditeur crée une nouvelle branche dans votre dépôt, que toute personne ayant accès au dépôt peut utiliser pour collaborer et examiner les modifications.
* **Publiez sur votre branche de déploiement** : l&#39;éditeur crée un commit et le pousse directement vers votre branche de déploiement, ce qui publie immédiatement vos modifications.
* **Publiez sur d&#39;autres branches** : l&#39;éditeur crée une pull request, ce qui vous permet d&#39;obtenir des retours avant de fusionner vos modifications dans votre branche de déploiement.

<div id="common-workflows">
  ## Flux de travail courants
</div>

<div id="publish-directly-to-your-deployment-branch">
  ### Publier directement sur votre branche de déploiement
</div>

<Tabs>
  <Tab title="Avec l’éditeur web">
    1. Ouvrez le fichier dans l’[éditeur web](https://dashboard.mintlify.com/editor).
    2. Effectuez vos modifications.
    3. Cliquez sur **Publish**.
    4. Les modifications apparaissent dans le dépôt et sont déployées automatiquement.
  </Tab>

  <Tab title="En développement local">
    1. Récupérez les dernières modifications : `git pull`
    2. Modifiez le fichier dans votre éditeur.
    3. Ajoutez les modifications à l’index : `git add filename.mdx`
    4. Validez : `git commit -m "Update documentation"`
    5. Poussez : `git push`
    6. Les modifications sont déployées automatiquement.
  </Tab>
</Tabs>

<div id="work-on-a-feature-branch">
  ### Travailler sur une branche de fonctionnalité
</div>

<Tabs>
  <Tab title="Utiliser l’éditeur web">
    <Note>
      Pour créer des pull requests depuis l’éditeur web, vous devez avoir activé une règle de protection de branche imposant le passage par des pull requests avant que les modifications puissent être fusionnées dans votre branche de déploiement. Sans règle de protection de branche, les modifications apportées sur des branches sont fusionnées dans votre branche de déploiement lors de la publication.
    </Note>

    1. Créez une branche à partir du menu déroulant des branches dans la barre d’outils de l’éditeur.
    2. Apportez et enregistrez les modifications sur la branche.
    3. Cliquez sur **Publish** pour créer une pull request.
    4. Fusionnez la pull request lorsque vous êtes prêt.
  </Tab>

  <Tab title="Utiliser le développement local">
    1. Créez une branche : `git checkout -b feature-name`
    2. Apportez les modifications et validez-les.
    3. Poussez la branche : `git push -u origin feature-name`
    4. Créez une pull request.
    5. Fusionnez la pull request lorsque vous êtes prêt.
  </Tab>
</Tabs>

<div id="review-changes-before-publishing">
  ### Passez en revue les modifications avant de publier
</div>

<Steps>
  <Step title="Créez une branche de fonctionnalité.">
    Travaillez sur les modifications dans une branche distincte de votre branche de déploiement afin de pouvoir les partager et les relire avant de les publier.
  </Step>

  <Step title="Apportez vos modifications.">
    Modifiez les fichiers et validez les changements dans la branche de fonctionnalité.
  </Step>

  <Step title="Créez une pull request.">
    Créez une pull request pour proposer la fusion des modifications de votre branche de fonctionnalité dans la branche de déploiement.
  </Step>

  <Step title="Examinez le diff.">
    Vérifiez vos modifications. La pull request affiche les différences ligne par ligne par rapport à la version d&#39;origine du fichier.
  </Step>

  <Step title="Recueillez les retours de l'équipe.">
    Les membres de l&#39;équipe peuvent commenter des lignes précises ou l&#39;ensemble des modifications. Apportez les changements nécessaires et validez-les dans la branche de fonctionnalité.
  </Step>

  <Step title="Fusionnez après approbation.">
    Fusionnez la pull request pour publier les modifications dans votre documentation en ligne.
  </Step>
</Steps>

<div id="git-best-practices">
  ## Bonnes pratiques Git
</div>

Chaque équipe a ses propres flux de travail et préférences, mais voici quelques bonnes pratiques générales pour bien démarrer.

* **Rédigez des messages de commit explicites** : indiquez clairement ce qui a changé en utilisant des formulations actives. `Fix broken link in API docs` est plus informatif que `update page`.
* **Utilisez des noms de branche explicites** : les noms de branche doivent indiquer clairement leur objectif. Utilisez des noms précis comme `update-api-reference` plutôt que des noms génériques comme `temp` ou `my-branch`.
* **Gardez des branches ciblées** : limitez les modifications d’une branche à une tâche ou à un projet précis. Cela facilite les revues et réduit les conflits.
* **Supprimez les branches après la fusion** : supprimez les branches lorsque vous n’en avez plus besoin pour garder votre dépôt bien organisé.
* **Récupérez les changements avant de pousser** : récupérez toujours les dernières modifications avant de pousser pour éviter les conflits. L’éditeur web le fait automatiquement.
* **Relisez d’abord vos propres modifications** : vérifiez le diff avant de créer une pull request.
