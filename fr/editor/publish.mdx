<div id="publishing-workflows">
  ## Workflows de publication
</div>

L'éditeur prend en charge deux workflows pour publier des mises à jour de la documentation. Le workflow que vous utilisez dépend des règles de protection des branches de votre dépôt et de la branche sur laquelle vous travaillez.

* **Créer des pull requests** : si votre dépôt a une règle de protection de branche qui impose des pull requests avant que les modifications puissent être fusionnées dans votre branche de déploiement, l'éditeur crée une pull request lorsque vous publiez des modifications.
* **Publier directement** : si votre dépôt n'a pas de règles de protection de branche, vos modifications sont fusionnées dans la branche de déploiement et déployées immédiatement lorsque vous publiez.

| Type de branche | Protection de branche | Workflow de publication |
|-------------|-------------------|------------------------------|
| <Tooltip headline="Branche de déploiement" tip="La branche qui publie sur votre site de documentation en production, généralement « main ».">Branche de déploiement</Tooltip> | Aucune | Valide et déploie les modifications |
| Branche de déploiement | Pull requests requises | Crée une pull request |
| <Tooltip headline="Branche de fonctionnalité" tip="Une branche isolée sur laquelle vous travaillez sur des mises à jour avant de les fusionner dans votre branche de déploiement.">Branche de fonctionnalité</Tooltip> | Aucune | Fusionne les modifications dans la branche de déploiement et déploie les modifications |
| Branche de fonctionnalité | Pull requests requises | Crée une pull request |

<Tip>
  Configurez des règles de protection de branche dans votre fournisseur Git pour imposer des pull requests. Consultez [À propos des branches protégées](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) dans la documentation GitHub ou [Branches protégées](https://docs.gitlab.com/user/project/repository/branches/protected/) dans la documentation GitLab.
</Tip>

<div id="save-changes">
  ## Enregistrer les modifications
</div>

Au fur et à mesure que vous modifiez le contenu, l’éditeur suit vos modifications.

- Fichiers ajoutés ou supprimés.
- Modifications de contenu dans les pages.
- Changements dans la structure de navigation.
- Importation et organisation des médias.
- Mises à jour de la configuration.

Lorsque vous travaillez sur votre branche de déploiement, vos modifications sont enregistrées automatiquement.

Pour annuler des modifications, cliquez sur **Undo changes** à côté du nom d’un fichier dans la liste déroulante **Changes**.

<div id="publish-your-changes">
  ### Publier vos modifications
</div>

Cliquez sur **Publish** dans la barre d’outils. Selon votre flux de travail, vos modifications sont déployées immédiatement ou une pull request est créée pour que vous puissiez la fusionner dans votre dépôt Git. Si vous êtes sur une branche de fonctionnalité, enregistrez vos modifications avant de les publier.

Le bouton **Publish** est désactivé lorsqu’il n’y a aucune modification en attente ou qu’une pull request pour la branche actuelle est déjà ouverte.

## Résoudre les conflits

Les conflits se produisent lorsque votre branche et la branche de déploiement comportent des modifications incompatibles dans les mêmes fichiers.

<div id="what-causes-conflicts">
  ### Ce qui provoque des conflits
</div>

Les conflits surviennent lorsque :

- Vous et un autre membre de l'équipe modifiez les mêmes lignes dans un fichier.
- Des fichiers sont déplacés ou supprimés dans une branche et modifiés dans une autre.

<div id="resolve-conflicts">
  ### Résoudre les conflits
</div>

L’éditeur affiche des avertissements lorsque des conflits empêchent des opérations comme la publication ou le passage à une autre branche. Pour les résoudre, suivez les instructions de l’éditeur pour choisir les modifications à conserver.

<div id="commit-signing">
  ## Signature de commits
</div>

Signez vos commits avec votre compte GitHub en l’autorisant dans vos [paramètres de compte](https://dashboard.mintlify.com/settings/account). Sans cette autorisation, l’application GitHub Mintlify signe les commits effectués dans l’éditeur web.

Attribuer les commits à votre compte permet de conserver un historique précis des personnes ayant modifié votre documentation.
