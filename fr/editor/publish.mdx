<div id="publishing-workflows">
  ## Workflows de publication
</div>

L’éditeur prend en charge deux workflows pour publier les mises à jour de la documentation. Le workflow que vous utilisez dépend des règles de protection des branches de votre dépôt et de la branche sur laquelle vous travaillez.

* **Créer des pull requests** : si votre dépôt comporte une règle de protection des branches qui exige des pull requests avant que les modifications puissent être fusionnées dans votre branche de déploiement, l’éditeur crée une pull request lorsque vous publiez vos modifications.
* **Publier directement** : si votre dépôt n’a aucune règle de protection des branches, vos modifications sont fusionnées dans la branche de déploiement et déployées immédiatement lorsque vous publiez.

| Type de branche                                                                                                                                                                                         | Protection de branche  | Workflow de publication                                                  |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------ |
| <Tooltip headline="Branche de déploiement" tip="Branche qui publie votre site de documentation en production, généralement 'main'.">Branche de déploiement</Tooltip>                                    | Aucune                 | Effectue un commit et déploie les modifications                          |
| Branche de déploiement                                                                                                                                                                                  | Pull requests requises | Crée une pull request                                                    |
| <Tooltip headline="Branche de fonctionnalité" tip="Branche isolée sur laquelle vous travaillez avant de fusionner vos mises à jour dans la branche de déploiement.">Branche de fonctionnalité</Tooltip> | Aucune                 | Fusionne les modifications dans la branche de déploiement et les déploie |
| Branche de fonctionnalité                                                                                                                                                                               | Pull requests requises | Crée une pull request                                                    |

<Tip>
  Configurez des règles de protection des branches dans votre fournisseur Git pour exiger des pull requests. Consultez [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) dans la documentation GitHub ou [Protected branches](https://docs.gitlab.com/user/project/repository/branches/protected/) dans la documentation GitLab.
</Tip>

<div id="save-changes">
  ## Enregistrer les modifications
</div>

Au fur et à mesure de vos modifications, l’éditeur suit vos changements.

* Fichiers ajoutés ou supprimés.
* Modifications du contenu des pages.
* Modifications de la structure de navigation.
* Importation et organisation des médias.
* Mises à jour de la configuration.

Lorsque vous travaillez sur votre branche de déploiement, vos modifications sont enregistrées automatiquement.

Pour annuler des modifications, cliquez sur **Annuler les modifications** à côté d’un nom de fichier dans le menu déroulant **Modifications**.

<div id="publish-your-changes">
  ### Publier vos modifications
</div>

Cliquez sur **Publier** dans la barre d’outils. Selon votre flux de travail, vos modifications sont déployées immédiatement ou une pull request est créée pour que vous la fusionniez dans votre hébergeur Git. Si vous êtes sur une branche de fonctionnalité, enregistrez vos modifications avant de publier.

Le bouton **Publier** est désactivé lorsqu’il n’y a aucune modification en attente ou qu’une pull request pour la branche actuelle est déjà ouverte.

## Résoudre les conflits

Les conflits surviennent lorsque votre branche et la branche de déploiement contiennent des modifications incompatibles dans les mêmes fichiers.

<div id="what-causes-conflicts">
  ### Ce qui provoque des conflits
</div>

Les conflits surviennent lorsque :

* Vous et un autre membre de l’équipe modifiez les mêmes lignes d’un fichier.
* Des fichiers sont déplacés ou supprimés dans une branche, mais modifiés dans une autre.

<div id="resolve-conflicts">
  ### Résoudre les conflits
</div>

L’éditeur affiche des avertissements lorsque des conflits empêchent certaines opérations, comme la publication ou le changement de branche. Pour résoudre les conflits, suivez les instructions affichées dans l’éditeur pour choisir les modifications à conserver.

<div id="commit-signing">
  ## Signature des commits
</div>

Signez les commits avec votre compte GitHub en l’autorisant dans les [paramètres de votre compte](https://dashboard.mintlify.com/settings/account). Sans cette autorisation, l’application GitHub de Mintlify signe les commits effectués dans l’éditeur web.

Associer les commits à votre compte permet de conserver un historique précis des modifications apportées à votre documentation et de leurs auteurs.
