Le playground d’API est un environnement interactif qui permet aux utilisateurs de tester et d’explorer vos endpoints d’API. Les développeurs peuvent composer des requêtes d’API, les envoyer et consulter les réponses sans quitter votre documentation.

Consultez [Déclencher une mise à jour](/fr/api/update/trigger) pour voir un exemple du playground d’API en action.

Le playground génère des pages interactives pour vos endpoints à partir de votre spécification OpenAPI ou de votre schéma AsyncAPI. Si vous modifiez votre API, le playground met automatiquement à jour les pages correspondantes.

Nous recommandons de générer votre playground d’API à partir d’une spécification OpenAPI. Toutefois, vous pouvez créer manuellement des pages de référence d’API après avoir défini une URL de base et une méthode d’authentification dans votre `docs.json`.

<div id="get-started">
  ## Premiers pas
</div>

<Steps>
  <Step title="Ajoutez votre fichier de spécification OpenAPI.">
    <Tip>
      Validez votre fichier de spécification OpenAPI à l’aide de [Swagger Editor](https://editor.swagger.io/) ou de la commande [Mint CLI](https://www.npmjs.com/package/mint) `mint openapi-check <filename>`.
    </Tip>

    ```bash {3}
    /your-project
      |- docs.json
      |- openapi.json
    ```
  </Step>

  <Step title="Générez les pages d’endpoints.">
    Mettez à jour votre fichier `docs.json` afin qu’il référence votre spécification OpenAPI.

    **Pour générer automatiquement des pages pour tous les endpoints de votre spécification OpenAPI**, ajoutez une propriété `openapi` à n’importe quel élément de navigation.

    Cet exemple génère une page pour chaque endpoint spécifié dans `openapi.json` et organise les pages dans le groupe « API reference ».

    ```json Générer toutes les pages d’endpoints
    "navigation": {
      "groups": [
        {
          "group": "API reference",
          "openapi": "openapi.json"
        }
      ]
    }
    ```

    **Pour générer des pages uniquement pour certains endpoints**, indiquez ces endpoints dans la propriété `pages` de l’élément de navigation.

    Cet exemple génère des pages uniquement pour les endpoints `GET /users` et `POST /users`. Pour générer d’autres pages d’endpoints, ajoutez des endpoints supplémentaires au tableau `pages`.

    ```json Générer des pages d’endpoints spécifiques
    "navigation": {
      "groups": [
          {
            "group": "API reference",
            "openapi": "openapi.json",
            "pages": [
              "GET /users",
              "POST /users"
            ]
          }
      ]
    }
    ```
  </Step>
</Steps>

<div id="customize-your-playground">
  ## Personnaliser votre espace de test
</div>

Personnalisez votre espace de test d&#39;API en définissant les propriétés suivantes dans votre `docs.json`.

<ResponseField name="playground" type="object">
  Paramètres de configuration de l&#39;espace de test de l&#39;API.

  <Expandable title="playground" defaultOpen="True">
    <ResponseField name="display" type="&#x22;interactive&#x22; | &#x22;simple&#x22; | &#x22;none&#x22; | &#x22;auth&#x22;">
      Le mode d&#39;affichage de l&#39;espace de test de l&#39;API.

      * `"interactive"` : affiche l&#39;espace de test interactif.
      * `"simple"` : affiche un endpoint copiable sans espace de test.
      * `"none"` : n&#39;affiche rien.
      * `"auth"` : affiche l&#39;espace de test interactif uniquement pour les utilisateurs authentifiés. Les utilisateurs non authentifiés ou ne faisant pas partie des groupes requis ne voient aucun espace de test.

      La valeur par défaut est `interactive`.
    </ResponseField>

    <ResponseField name="proxy" type="boolean" defaultOpen="True">
      Indique s&#39;il faut faire passer les requêtes d&#39;API via un serveur proxy. La valeur par défaut est `true`.
    </ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="examples" type="object">
  Paramètres de configuration pour les exemples d&#39;API générés automatiquement.

  <Expandable title="examples" defaultOpen="True">
    <ResponseField name="languages" type="array of string">
      Langages d&#39;exemple pour les extraits d&#39;API générés automatiquement.

      Les langages s&#39;affichent dans l&#39;ordre spécifié.
    </ResponseField>

    <ResponseField name="defaults" type="&#x22;required&#x22; | &#x22;all&#x22;">
      Indique s&#39;il faut afficher les paramètres optionnels dans les exemples d&#39;API. La valeur par défaut est `all`.
    </ResponseField>

    <ResponseField name="prefill" type="boolean">
      Indique s&#39;il faut préremplir l&#39;espace de test de l&#39;API avec des données provenant des exemples de schéma. Lorsque cette option est activée, l&#39;espace de test remplit automatiquement les champs de requête avec des valeurs d&#39;exemple issues de votre spécification OpenAPI. La valeur par défaut est `false`.
    </ResponseField>

    <ResponseField name="autogenerate" type="boolean">
      Indique s&#39;il faut générer des exemples de code pour les endpoints à partir des spécifications d&#39;API. La valeur par défaut est `true`. Lorsqu&#39;elle est définie sur `false`, seuls les exemples de code rédigés manuellement (provenant de `x-codeSamples` dans les spécifications OpenAPI ou de composants `<RequestExample>` dans le MDX) apparaissent dans l&#39;espace de test de l&#39;API.
    </ResponseField>
  </Expandable>
</ResponseField>

<div id="example-configuration">
  ### Exemple de configuration
</div>

Cet exemple configure l’espace de test de l’API pour le rendre interactif, avec des exemples de code pour cURL, Python et JavaScript. Seuls les paramètres obligatoires sont affichés dans les extraits de code, et l’espace de test préremplit le corps de la requête avec des valeurs d’exemple.

```json
{
 "api": {
   "playground": {
     "display": "interactive"
   },
   "examples": {
     "languages": ["curl", "python", "javascript"],
     "defaults": "required",
     "prefill": true
   }
 }
}
```

<div id="auth-based-playground-display">
  ### Affichage du playground basé sur l’authentification
</div>

Utilisez le mode d’affichage `auth` pour n’afficher le playground interactif qu’aux utilisateurs authentifiés. Il est utile lorsque vous souhaitez permettre aux utilisateurs de consulter publiquement la documentation de votre API tout en limitant l’accès au playground aux utilisateurs connectés.

Lorsque `display` est défini sur `auth` :

* Les utilisateurs authentifiés voient le playground interactif.
* Les utilisateurs non authentifiés ne voient aucun playground (équivalent à `none`).

Vous pouvez également combiner `auth` avec la propriété `groups` dans le frontmatter de la page afin de limiter l’accès au playground à certains groupes d’utilisateurs spécifiques.

```mdx Page with group-restricted playground
---
title: "Create user"
openapi: POST /users
playground: auth
groups: ["admin", "developer"]
public: true
---
```

Dans cet exemple :

* La page est visible publiquement (tout le monde peut consulter la documentation).
* Seuls les utilisateurs authentifiés appartenant aux groupes `admin` ou `developer` voient le bac à sable interactif.
* Les utilisateurs qui ne font pas partie de ces groupes ne voient aucun bac à sable.

Si la page ne définit pas de propriété `groups`, tous les utilisateurs authentifiés voient le bac à sable interactif.

<Note>
  Le mode d’affichage `auth` nécessite que [l’authentification](/fr/deploy/authentication-setup) soit configurée pour votre documentation.
</Note>

<div id="custom-endpoint-pages">
  ### Pages d’endpoint personnalisées
</div>

Lorsque vous avez besoin de mieux contrôler votre documentation d’API, utilisez l’extension `x-mint` dans votre spécification OpenAPI ou créez des pages MDX individuelles pour vos endpoints.

Les deux options vous permettent de :

* Personnaliser les métadonnées de la page
* Ajouter du contenu supplémentaire, comme des exemples
* Contrôler le comportement du playground pour chaque page

L’extension `x-mint` est recommandée afin que l’ensemble de votre documentation d’API soit automatiquement généré à partir de votre spécification OpenAPI et conservé dans un seul fichier.

Les pages MDX individuelles sont recommandées pour les petites API ou lorsque vous souhaitez tester des modifications page par page.
