OpenAPI est une spécification qui permet de décrire des API. Mintlify prend en charge les documents OpenAPI 3.0 et 3.1 pour générer une documentation API interactive et la maintenir à jour.

<div id="add-an-openapi-specification-file">
  ## Ajouter un fichier de spécification OpenAPI
</div>

Pour documenter vos endpoints avec OpenAPI, vous avez besoin d’une ou de plusieurs spécifications OpenAPI valides au format JSON ou YAML, conformes à la [spécification OpenAPI 3.0 ou 3.1](https://swagger.io/specification/).

Ajoutez les spécifications OpenAPI à votre dépôt de documentation ou hébergez-les en ligne afin de pouvoir y accéder via une URL.

Référencez autant de spécifications OpenAPI que nécessaire dans l’élément de navigation de votre `docs.json` pour créer des pages pour vos endpoints d’API. Chaque fichier de spécification génère son propre ensemble d’endpoints.

<CodeGroup>
  ```json Spécification unique
  "navigation": {
    "tabs": [
      {
        "tab": "API Reference",
        "openapi": "openapi.json"
      }
    ]
  }
  ```

  ```json Spécifications multiples
  "navigation": {
    "tabs": [
      {
        "tab": "API Reference",
        "openapi": [
          "openapi/v1.json",
          "openapi/v2.json"
        ]
      }
    ]
  }
  ```
</CodeGroup>

<Note>
  Mintlify prend en charge `$ref` pour les **références internes uniquement** au sein d’un seul document OpenAPI. Les références externes ne sont pas prises en charge.
</Note>

<div id="describe-your-api">
  ### Décrivez votre API
</div>

Nous vous recommandons les ressources suivantes pour vous familiariser avec OpenAPI et rédiger votre spécification.

* [Le guide OpenAPI de Swagger](https://swagger.io/docs/specification/v3_0/basic-structure/) pour découvrir la syntaxe d&#39;OpenAPI.
* [Les sources Markdown de la spécification OpenAPI](https://github.com/OAI/OpenAPI-Specification/blob/main/versions/) pour consulter les détails de la dernière version de la spécification OpenAPI.
* [Swagger Editor](https://editor.swagger.io/) pour modifier, valider et déboguer votre document OpenAPI.
* [Mint CLI](https://www.npmjs.com/package/mint) pour valider votre document OpenAPI avec la commande : `mint openapi-check <openapiFilenameOrUrl>`.

<Note>
  Le guide OpenAPI de Swagger porte sur OpenAPI v3.0, mais la quasi-totalité des informations s&#39;applique aussi à la v3.1. Pour en savoir plus sur les différences entre les versions v3.0 et v3.1, consultez [Migrating from OpenAPI 3.0 to 3.1.0](https://www.openapis.org/blog/2021/02/16/migrating-from-openapi-3-0-to-3-1-0) sur le blog OpenAPI.
</Note>

<div id="specify-the-base-url-for-your-api">
  ### Spécifiez l’URL de base de votre API
</div>

Pour activer le Bac à sable API, ajoutez un champ `servers` à votre spécification OpenAPI contenant l’URL de base de votre API.

```json
{
  "servers": [
    {
      "url": "https://api.example.com/v1"
    }
  ]
}
```

Dans une spécification OpenAPI, les différents endpoints d&#39;API sont définis par leur chemin, comme `/users/{id}` ou simplement `/`. L&#39;URL de base indique à quelle adresse ces chemins doivent être ajoutés. Pour en savoir plus sur la configuration du champ `servers`, consultez [API Server and Base Path](https://swagger.io/docs/specification/api-host-and-base-path/) dans la documentation OpenAPI.

Le bac à sable API utilise ces URL de serveur pour déterminer où envoyer les requêtes. Si vous spécifiez plusieurs serveurs, un menu déroulant permet aux utilisateurs de passer d&#39;un serveur à l&#39;autre. Si vous ne spécifiez aucun serveur, le bac à sable API utilise le mode simple, car il ne peut pas envoyer de requêtes sans URL de base.

Si votre API comporte des endpoints accessibles à des URL différentes, vous pouvez [remplacer le champ `servers`](https://swagger.io/docs/specification/v3_0/api-host-and-base-path/#overriding-servers) pour un chemin ou une opération donnés.

<div id="specify-authentication">
  ### Configurer l&#39;authentification
</div>

Pour activer l&#39;authentification dans votre documentation API et votre bac à sable API, configurez les champs `securitySchemes` et `security` dans votre spécification OpenAPI. Les descriptions d&#39;API et le bac à sable API ajoutent des champs d&#39;authentification en fonction des paramètres de sécurité définis dans votre spécification OpenAPI.

<Steps>
  <Step title="Définissez votre méthode d'authentification.">
    Ajoutez un champ `securitySchemes` pour définir la méthode d&#39;authentification des utilisateurs.

    Cet exemple montre une configuration d&#39;authentification bearer.

    ```json
    {
      "components": {
        "securitySchemes": {
          "bearerAuth": {
            "type": "http",
            "scheme": "bearer"
          }
        }
      }
    }
    ```
  </Step>

  <Step title="Appliquez l'authentification à vos endpoints.">
    Ajoutez un champ `security` pour exiger une authentification.

    ```json
    {
      "security": [
        {
          "bearerAuth": []
        }
      ]
    }
    ```
  </Step>
</Steps>

Les types d&#39;authentification courants incluent :

* [Clés API](https://swagger.io/docs/specification/authentication/api-keys/) : Pour les clés transmises dans les en-têtes, les paramètres de requête ou les cookies.
* [Bearer](https://swagger.io/docs/specification/authentication/bearer-authentication/) : Pour les jetons JWT ou OAuth.
* [Basic](https://swagger.io/docs/specification/authentication/basic-authentication/) : Pour le nom d&#39;utilisateur et le mot de passe.

Si différents endpoints de votre API nécessitent des méthodes d&#39;authentification différentes, vous pouvez [redéfinir le champ `security`](https://swagger.io/docs/specification/authentication/#:~:text=you%20can%20apply%20them%20to%20the%20whole%20API%20or%20individual%20operations%20by%20adding%20the%20security%20section%20on%20the%20root%20level%20or%20operation%20level%2C%20respectively.) pour une opération donnée.

Pour en savoir plus sur la définition et l&#39;application de l&#39;authentification, consultez [Authentication](https://swagger.io/docs/specification/authentication/) dans la documentation OpenAPI.

<div id="customize-your-endpoint-pages">
  ## Personnalisez les pages de vos endpoints
</div>

Personnalisez les pages de vos endpoints en ajoutant l’extension `x-mint` à votre spécification OpenAPI. L’extension `x-mint` vous offre un contrôle accru sur la façon dont votre documentation d’API est générée et affichée.

<div id="metadata">
  ### Métadonnées
</div>

Remplacez les métadonnées par défaut des pages d’API générées en ajoutant `x-mint: metadata` à n’importe quelle opération. Vous pouvez utiliser n’importe quel champ de métadonnées valide dans le Frontmatter MDX, à l’exception de `openapi`.

```json {7-13}
{
  "paths": {
    "/users": {
      "get": {
        "summary": "Get users",
        "description": "Retrieve a list of users",
        "x-mint": {
          "metadata": {
            "title": "List all users",
            "description": "Fetch paginated user data with filtering options",
            "og:title": "Display a list of users"
          }
        },
        "parameters": [
          {
            // Configuration des paramètres
          }
        ]
      }
    }
  }
}
```

Vous pouvez également contrôler l’affichage du Bac à sable API pour chaque endpoint à l’aide des champs de métadonnées `playground` et `groups` :

```json {7-11}
{
  "paths": {
    "/admin/users": {
      "post": {
        "summary": "Create admin user",
        "x-mint": {
          "metadata": {
            "playground": "auth",
            "groups": ["admin"],
            "public": true
          }
        }
      }
    }
  }
}
```

Cette configuration rend la page accessible au public tout en réservant le Bac à sable API interactif aux utilisateurs authentifiés du groupe `admin`.

<div id="content">
  ### Contenu
</div>

Ajoutez du contenu avant la documentation d’API générée automatiquement à l’aide de `x-mint: content`. L’extension `x-mint: content` prend en charge tous les composants MDX et toute la mise en forme de Mintlify.

```json {6-8}
{
  "paths": {
    "/users": {
      "post": {
        "summary": "Create user",
        "x-mint": {
          "content": "## Prérequis\n\nCet endpoint nécessite des privilèges d'administrateur et est soumis à une limitation de débit.\n\n<Note>Les adresses e-mail des utilisateurs doivent être uniques dans le système.</Note>"
        },
        "parameters": [
          {
            // Configuration des paramètres
          }
        ]
      }
    }
  }
}
```

<div id="href">
  ### Href
</div>

Définissez l’URL de la page d’endpoint générée automatiquement à l’aide de `x-mint: href`. Lorsque `x-mint: href` est présent, la page API générée utilise l’URL indiquée au lieu de l’URL générée automatiquement par défaut.

```json {6-8, 14-16}
{
  "paths": {
    "/legacy-endpoint": {
      "get": {
        "summary": "Legacy endpoint",
        "x-mint": {
          "href": "/deprecated-endpoints/legacy-endpoint"
        }
      }
    },
    "/documented-elsewhere": {
      "post": {
        "summary": "Special endpoint",
        "x-mint": {
          "href": "/guides/special-endpoint-guide"
        }
      }
    }
  }
}
```

<div id="auto-populate-api-pages">
  ## Générer automatiquement des pages d’API
</div>

Ajoutez un champ `openapi` à n’importe quel élément de navigation dans votre `docs.json` pour générer automatiquement des pages pour les endpoints OpenAPI. Vous pouvez choisir où ces pages apparaissent dans votre structure de navigation, dans des sections d’API dédiées ou aux côtés d’autres pages.

Le champ `openapi` accepte soit un chemin de fichier dans le dépôt de votre documentation, soit l’URL d’un document OpenAPI hébergé.

Les pages d’endpoint générées utilisent ces valeurs de métadonnées par défaut :

* `title` : le champ `summary` de l’opération, s’il est présent. En l’absence de `summary`, le titre est généré à partir de la méthode HTTP et de l’endpoint.
* `description` : le champ `description` de l’opération, s’il est présent.
* `version` : la valeur `version` de l’ancre ou de l’onglet parent, si elle est présente.
* `deprecated` : le champ `deprecated` de l’opération. Si sa valeur est `true`, un libellé d’obsolescence apparaît à côté du titre de l’endpoint dans la navigation latérale et sur la page de l’endpoint.

<Tip>
  Pour exclure certains endpoints de vos pages d’API générées automatiquement, ajoutez la propriété [x-hidden](/fr/api-playground/managing-page-visibility#x-hidden) à l’opération dans votre spécification OpenAPI.
</Tip>

Il existe deux façons d’ajouter des pages d’endpoint à votre documentation :

1. **Sections d’API dédiées** : référencez des spécifications OpenAPI dans des éléments de navigation pour créer des sections d’API dédiées.
2. **Endpoints sélectionnés** : référencez des endpoints spécifiques dans votre navigation aux côtés d’autres pages.

<div id="dedicated-api-sections">
  ### Sections d’API dédiées
</div>

Générez des sections d’API dédiées en ajoutant un champ `openapi` à un élément de navigation, sans y ajouter d’autres pages. Tous les endpoints de la spécification sont inclus.

```json {5}
"navigation": {
  "tabs": [
    {
        "tab": "API Reference",
        "openapi": "https://petstore3.swagger.io/api/v3/openapi.json"
    }
  ]
}
```

Pour organiser plusieurs spécifications OpenAPI dans des sections distinctes de votre documentation, attribuez chaque spécification à un groupe différent dans la hiérarchie de navigation. Chaque groupe peut faire référence à sa propre spécification OpenAPI.

```json {8-11, 15-18}
"navigation": {
  "tabs": [
    {
      "tab": "API Reference",
      "groups": [
        {
          "group": "Users API",
          "openapi": {
            "source": "/path/to/users-openapi.json",
            "directory": "users-api-reference"
          }
        },
        {
          "group": "Admin API",
          "openapi": {
            "source": "/path/to/admin-openapi.json",
            "directory": "admin-api-reference"
          }
        }
      ]
    }
  ]
}
```

<Note>
  Le champ `directory` est facultatif et indique où sont stockées les pages d’API générées dans votre dépôt de documentation. S’il n’est pas renseigné, le répertoire `api-reference` de votre dépôt est utilisé par défaut.
</Note>

<div id="selective-endpoints">
  ### Endpoints sélectionnés
</div>

Lorsque vous souhaitez mieux contrôler l’emplacement des endpoints dans votre documentation, vous pouvez faire référence à des endpoints spécifiques dans votre navigation. Cette approche vous permet de générer des pages pour des endpoints d’API aux côtés d’autres contenus. Vous pouvez également l’utiliser pour combiner des endpoints issus de différentes spécifications OpenAPI.

<div id="set-a-default-openapi-spec">
  #### Définir une spécification OpenAPI par défaut
</div>

Configurez une spécification OpenAPI par défaut pour un élément de navigation. Faites ensuite référence à des endpoints spécifiques dans le champ `pages`.

```json {12, 15-16}
"navigation": {
  "tabs": [
    {
      "tab": "Getting started",
      "pages": [
        "quickstart",
        "installation"
      ]
    },
    {
      "tab": "API reference",
      "openapi": "/path/to/openapi.json",
      "pages": [
        "api-overview",
        "GET /users",
        "POST /users",
        "guides/authentication"
      ]
    }
  ]
}
```

Toute entrée de page au format `METHOD /path` génère une page d’API pour cet endpoint à l’aide de la spécification OpenAPI par défaut.

<div id="openapi-spec-inheritance">
  #### Héritage des spécifications OpenAPI
</div>

Les spécifications OpenAPI se transmettent dans toute la hiérarchie de navigation. Les éléments de navigation enfants héritent de la spécification OpenAPI de leur parent, sauf s’ils définissent la leur.

```json {3, 7-8, 11, 13-14}
{
  "group": "API reference",
  "openapi": "/path/to/openapi-v1.json",
  "pages": [
    "overview",
    "authentication",
    "GET /users",
    "POST /users",
    {
      "group": "Orders",
      "openapi": "/path/to/openapi-v2.json",
      "pages": [
        "GET /orders",
        "POST /orders"
      ]
    }
  ]
}
```

<div id="individual-endpoints">
  #### Endpoints individuels
</div>

Faites référence à des endpoints spécifiques sans définir de spécification OpenAPI par défaut, en indiquant le chemin du fichier. Vous pouvez faire référence à des endpoints issus de plusieurs spécifications OpenAPI dans une même section de la documentation.

```json {5-6}
"navigation": {
  "pages": [
    "introduction",
    "user-guides",
    "/path/to/users-openapi.json POST /users",
    "/path/to/orders-openapi.json GET /orders"
  ]
}
```

Cette approche est utile lorsque vous avez besoin d&#39;endpoints individuels issus de différentes spécifications, que vous souhaitez n&#39;inclure que certains endpoints, ou inclure des endpoints aux côtés d&#39;autres types de documentation.

<div id="create-mdx-pages-from-your-openapi-specification">
  ## Créer des pages MDX à partir de votre spécification OpenAPI
</div>

Pour un contrôle plus précis de chaque page d’endpoint, créez des pages MDX à partir de votre spécification OpenAPI. Vous pouvez ainsi personnaliser les métadonnées et le contenu des pages, réorganiser les pages dans votre navigation ou en exclure, tout en continuant à utiliser les paramètres et les réponses générés automatiquement.

Il existe deux façons de documenter votre spécification OpenAPI avec des pages MDX individuelles :

* Documentez les endpoints avec le champ `openapi` dans le Frontmatter.
* Documentez les modèles de données avec le champ `openapi-schema` dans le Frontmatter.

<div id="document-endpoints">
  ### Documenter les endpoints
</div>

Créez une page pour chaque endpoint et indiquez quelle opération OpenAPI afficher à l’aide du champ `openapi` dans le frontmatter.

<CodeGroup>
  ```mdx Example
  ---
  title: "Get users"
  description: "Returns all plants from the system that the user has access to"
  openapi: "/path/to/openapi-1.json GET /users"
  deprecated: true
  version: "1.0"
  ---
  ```

  ```mdx Format
  ---
  title: "title of the page"
  description: "description of the page"
  openapi: openapi-file-path method path
  deprecated: boolean (not required)
  version: "version-string" (not required)
  ---
  ```
</CodeGroup>

La méthode et le chemin doivent correspondre exactement à votre spécification OpenAPI. Si vous avez plusieurs spécifications OpenAPI, incluez le chemin du fichier dans votre référence. Vous pouvez référencer des URL OpenAPI externes dans `docs.json`.

<div id="autogenerate-endpoint-pages">
  #### Générer automatiquement des pages d’endpoint
</div>

Pour générer automatiquement des fichiers MDX à partir de votre spécification OpenAPI, utilisez le [scraper](https://www.npmjs.com/package/@mintlify/scraping) Mintlify.

```bash
npx @mintlify/scraping@latest openapi-file <path-to-openapi-file> -o <folder-name>
```

<Tip>
  Ajoutez l’option `-o` pour indiquer le dossier dans lequel placer les fichiers. Si aucun dossier n’est spécifié, les fichiers seront placés dans le répertoire de travail.
</Tip>

<div id="document-data-models">
  ### Documentez les modèles de données
</div>

Créez une page pour chaque structure de données définie dans `components.schemas` de votre spécification OpenAPI à l’aide du champ `openapi-schema` dans le Frontmatter.

<CodeGroup>
  ```mdx Example
  ---
  openapi-schema: OrderItem
  ---
  ```

  ```mdx Format
  ---
  openapi-schema: "openapi-file-path schema-key"
  ---
  ```
</CodeGroup>

Si vous avez des schémas portant le même nom dans plusieurs fichiers, indiquez le fichier OpenAPI :

<CodeGroup>
  ```mdx Example
  ---
  openapi-schema: en-schema.json OrderItem
  ---
  ```

  ```mdx Format
  ---
  openapi-schema: "path-to-schema-file schema-key"
  ---
  ```
</CodeGroup>

<div id="webhooks">
  ## Webhooks
</div>

Les webhooks sont des rappels HTTP envoyés par votre API pour avertir des systèmes externes lorsqu&#39;un événement se produit. Les webhooks sont pris en charge dans les documents OpenAPI 3.1+.

Ajoutez un champ `webhooks` à votre document OpenAPI à côté du champ `paths`.

Pour plus d&#39;informations sur la définition des webhooks, consultez [Webhooks](https://spec.openapis.org/oas/v3.1.0#oasWebhooks) dans la documentation OpenAPI.

Pour créer une page MDX pour un webhook (OpenAPI 3.1+), utilisez `webhook` au lieu d&#39;une méthode HTTP :

```mdx
---
title: "Webhook de mise à jour de commande"
description: "Déclenché lorsqu'une commande est mise à jour"
openapi: "openapi.json webhook orderUpdated"
---
```

Le nom du webhook doit correspondre exactement à la clé du champ `webhooks` de votre spécification OpenAPI.
