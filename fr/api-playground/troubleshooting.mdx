Si vos pages d’API ne s’affichent pas correctement, vérifiez les problèmes de configuration courants suivants.

<AccordionGroup>
  <Accordion title="Toutes mes pages OpenAPI sont entièrement vides">
    Dans ce cas, il est probable que Mintlify ne parvienne pas à trouver votre document OpenAPI,
    ou que votre document OpenAPI ne soit pas valide.

    L’exécution de `mint dev` en local devrait permettre de faire apparaître certains de ces problèmes.

    Pour vérifier que votre document OpenAPI passe la validation :

    1. Ouvrez [ce validateur](https://editor.swagger.io/)
    2. Accédez à l’onglet &quot;Validate text&quot;
    3. Collez votre document OpenAPI
    4. Cliquez sur &quot;Validate it!&quot;

    Si la zone de texte qui apparaît en dessous a une bordure verte, votre document a bien passé la validation.
    Mintlify utilise exactement le même package de validation pour valider les documents OpenAPI. Donc, si votre document
    passe la validation ici, il y a de fortes chances que le problème vienne d’ailleurs.

    Par ailleurs, Mintlify ne prend pas en charge OpenAPI 2.0. Si votre document utilise cette version de la spécification,
    vous risquez de rencontrer ce problème. Vous pouvez convertir votre document dans [editor.swagger.io](https://editor.swagger.io/) (dans Edit &gt; Convert to OpenAPI 3) :

    <Frame>
      ![Capture d’écran du Swagger Editor avec le menu Edit ouvert et l’option de menu "Convert to OpenAPI 3" mise en évidence.](/images/convert-oas-3.png)
    </Frame>
  </Accordion>

  <Accordion title="L’une de mes pages OpenAPI est complètement vide">
    C’est généralement dû à un champ `openapi` mal orthographié dans les métadonnées de la page. Assurez-vous
    que la méthode HTTP et le chemin correspondent exactement à ceux indiqués dans le document OpenAPI.

    Voici un exemple de ce qui peut mal se passer :

    ```mdx get-user.mdx
    ---
    openapi: "GET /users/{id}/"
    ---
    ```

    ```yaml openapi.yaml
    paths:
      "/users/{id}":
        get: ...
    ```

    Notez que le chemin dans le champ `openapi` se termine par une barre oblique, tandis que le chemin dans le document OpenAPI
    n’en a pas.

    Un autre problème courant est une faute dans le nom de fichier. Si vous spécifiez un document OpenAPI particulier
    dans le champ `openapi`, assurez-vous que le nom de fichier est correct. Par exemple, si vous avez deux documents OpenAPI
    `openapi/v1.json` et `openapi/v2.json`, vos métadonnées peuvent ressembler à ceci :

    ```mdx api-reference/v1/users/get-user.mdx
    ---
    openapi: "v1 GET /users/{id}"
    ---
    ```
  </Accordion>

  <Accordion title="Les requêtes du Bac à sable API ne fonctionnent pas">
    Si vous avez configuré un nom de domaine personnalisé, il peut s&#39;agir d&#39;un problème lié à votre proxy inverse. Par
    défaut, les requêtes effectuées via le Bac à sable API commencent par une requête `POST` vers le
    chemin `/_mintlify/api/request` du site de documentation. Si votre proxy inverse est configuré pour n&#39;autoriser que les requêtes `GET`,
    toutes ces requêtes échoueront. Pour corriger ce problème, configurez votre proxy inverse de manière à
    autoriser les requêtes `POST` vers le chemin `/_mintlify/api/request`.

    Sinon, si votre proxy inverse ne vous permet pas d&#39;accepter les requêtes `POST`, vous pouvez configurer Mintlify pour envoyer les requêtes directement à votre backend à l&#39;aide du paramètre `api.playground.proxy` dans le `docs.json`, comme indiqué dans la [documentation des paramètres](/fr/organize/settings#param-proxy). Avec cette configuration, vous devrez configurer CORS sur votre serveur, car les requêtes proviendront directement du navigateur des utilisateurs au lieu de passer par votre proxy.
  </Accordion>

  <Accordion title="Les entrées de navigation OpenAPI ne créent pas de pages">
    Si vous utilisez une configuration de navigation OpenAPI, mais que les pages ne se génèrent pas, vérifiez les problèmes courants suivants :

    1. **Spécification OpenAPI par défaut manquante** : assurez-vous qu’un champ `openapi` est bien défini pour l’élément de navigation :

    ```json {5}
    "navigation": {
      "groups": [
        {
          "group": "API reference",
          "openapi": "/path/to/openapi.json",
          "pages": [
            "GET /users",
            "POST /users"
          ]
        }
      ]
    }
    ```

    2. **Héritage de la spécification OpenAPI** : si vous utilisez une navigation imbriquée, assurez-vous que les groupes enfants héritent de la bonne spécification OpenAPI, ou indiquez la leur.

    3. **Problèmes de validation** : utilisez `mint openapi-check <path-to-openapi-file>` pour vérifier que votre document OpenAPI est valide.
  </Accordion>

  <Accordion title="Certaines opérations OpenAPI apparaissent dans la navigation, mais d’autres n’y figurent pas">
    1. **Opérations masquées** : les opérations marquées par `x-hidden: true` dans votre spécification OpenAPI n’apparaîtront pas dans la navigation générée automatiquement.
    2. **Opérations invalides** : les opérations présentant des erreurs de validation dans la spécification OpenAPI peuvent être ignorées. Vérifiez votre document OpenAPI afin de repérer d’éventuelles erreurs de syntaxe.
    3. **Inclusion manuelle ou automatique** : si vous faites référence à des endpoints à partir d’une spécification OpenAPI, seules les opérations explicitement référencées apparaîtront dans la navigation. Aucune autre page ne sera ajoutée automatiquement. Cela inclut les opérations référencées dans des éléments de navigation enfants.
  </Accordion>

  <Accordion title="La navigation mixte (pages OpenAPI et MDX) ne fonctionne pas correctement">
    Lorsque vous combinez des opérations OpenAPI avec des pages de documentation classiques dans la navigation :

    1. **Conflits de fichiers** : vous ne pouvez pas avoir à la fois un fichier `MDX` et une entrée de navigation pour la même opération. Par exemple, si vous avez `get-users.mdx`, n’incluez pas non plus `"GET /users"` dans votre navigation. Si vous devez avoir un fichier qui porte le même nom qu’une opération, utilisez l’extension `x-mint` pour l’endpoint afin que le href pointe vers un autre emplacement.
    2. **Résolution des chemins** : les entrées de navigation qui ne correspondent pas à des opérations OpenAPI seront interprétées comme des chemins de fichier. Assurez-vous que vos fichiers `MDX` existent aux emplacements attendus.
    3. **Sensibilité à la casse** : la correspondance des opérations OpenAPI respecte la casse. Assurez-vous que les méthodes HTTP sont en majuscules dans les entrées de navigation.
  </Accordion>
</AccordionGroup>
